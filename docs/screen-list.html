1. OMS (주문)

주문 원장 영역. WMS 작업문서(입고예정·출고주문)의 발생지. 등록 폼과 목록·확정 관리 화면을 분리한다. 입고·출고 모두 작업문서의 생성·소멸은 여기서만 일어난다 — WMS 쪽에 등록·취소 화면을 두지 않는다.

화면주요 기능상태API
입고주문 벤더 발주 등록·수정 폼. 벤더/입고예정일/발주구분/담당자/비고 + 라인(상품·수량) 입력. 주문번호는 서버 채번(PO-YYYYMMDD-NNN)이고 수정해도 바뀌지 않는다. 경로에 id가 있으면 수정 모드(/oms/inbound-order/:id) — 작성(CREATED) 상태만 편집 가능하고 확정된 주문은 화면이 잠긴다 구현 POST /oms/inbound-orders
/oms/inbound-order
입고주문 관리 목록 검색(주문번호/벤더/상태/기간), 주문확정·확정취소·주문삭제. 확정이 ASN 생성의 유일한 기점이며, 목록에 생성된 입고번호와 창고 진행상태를 함께 표시. 주문번호를 누르면 수정 화면으로 이동한다.
상태는 CREATED ↔ CONFIRMED 둘뿐이다 — 취소 상태를 두지 않는다. 없앨 주문은 지우고(확정 전만), 확정된 주문은 확정취소로 되돌린 뒤 지운다. 삭제는 되돌릴 수 없으므로 확인 모달에 라인 건수를 함께 보여준다		 구현 GET /oms/inbound-orders, /{id}/lines
POST /{id}/confirm, /{id}/confirm-cancel
DELETE /{id}
/oms/inbound-orders
출고주문 점포 수주 등록·수정 폼. 납품처/출고예정일/출고유형/편수/담당자/비고 + 라인(상품·수량) 입력. 주문번호는 서버 채번(SO-YYYYMMDD-NNN)이고 수정해도 바뀌지 않는다. 경로에 id가 있으면 수정 모드(/oms/outbound-order/:id) — 작성(CREATED) 상태만 편집 가능하고 확정된 주문은 화면이 잠긴다.
출고유형·편수가 웨이브 편성 조건의 기준값이라 주문 시점에 정해진다. 수량은 출고단위 기준이라 환산 열이 없다(입고주문과 다른 점)		 구현 POST /oms/outbound-orders
GET /master/stores(납품처 팝업)
/oms/outbound-order
출고주문 관리 목록 검색(주문번호/납품처/상태/출고유형/편수/예정일), 주문확정·확정취소·주문삭제. 확정이 창고 출고주문 생성의 유일한 기점이며, 목록에 생성된 출고번호·창고 진행상태·편성된 웨이브를 함께 표시. 주문번호를 누르면 수정 화면으로 이동한다.
상태는 CREATED ↔ CONFIRMED 둘뿐이다 — 취소 상태를 두지 않는다. 확정취소는 웨이브 편성 전에만 된다(편성됐으면 웨이브에서 먼저 빼야 한다)		 구현 GET /oms/outbound-orders, /{id}/lines
POST /{id}/confirm, /{id}/confirm-cancel
DELETE /{id}
/oms/outbound-orders

결정됨 (2026-08-03): 출고도 입고와 같은 2계층으로 맞췄다. outb_order.oms_outb_order_id가 NOT NULL이라 주문 없는 창고 출고주문은 존재할 수 없고, WMS 등록 API(POST /outbound/orders)는 제거됐다. 확정과 창고 문서 생성은 OmsOutbOrderService.confirm()에서 한 트랜잭션으로 처리한다. 확정취소는 OutbOrder.requireRevertible()이 웨이브 편성 전까지만 허용한다. 창고 쪽 취소(outb_order의 CANCELLED · POST /outbound/orders/{id}/cancel)는 같은 「없앤다」가 두 갈래이던 것을 정리하며 폐지했다(migration-drop-outb-cancelled.sql). 출고예정일(expct_de)이 새로 생겨 웨이브 편성 대상 기간의 기준이 주문일에서 출고예정일로 바뀌었다.

결정됨 (2026-07-23): OMS 입고주문과 WMS 입고예정(ASN)의 관계는 ① 주문 확정 시 ASN 자동 생성. ib_order.oms_ib_order_id가 NOT NULL이라 주문 없는 ASN은 존재할 수 없고, ASN 등록 화면·API(POST /inbound/asns)는 제거됐다. 확정과 ASN 생성은 OmsIbOrderService.confirm()에서 한 트랜잭션으로 처리한다.

남은 한계: ASN을 취소해도 상위 주문은 CONFIRMED로 남는다(역방향 상태 전파 없음). 확정 후 주문 취소·수정은 미지원 — 되돌리려면 ASN을 취소해야 한다. 패키지는 com.project.omsback / com.project.wmsback로 분리했고 의존은 omsback → wmsback 한 방향만 허용한다(그래서 IbOrder는 OmsIbOrder를 연관관계가 아닌 스칼라 ID로 참조).

2. 입고 (Inbound)

화면주요 기능상태API
입고예정(ASN) 관리 목록 검색(입고번호/벤더/상태/기간), 취소. 헤더–라인 2단 구조. 등록 기능 없음 — ASN은 OMS 입고주문 확정으로만 생성된다 구현 GET /inbound/asns
/{id}/lines, /{id}/cancel
입고 검수 라인별 합격/불합격 수량 + 제조일자 입력 → Lot 채번 후 RCV-STAGE 입고. 하단에 검수 이력 + 건별 취소 구현 POST /{id}/receive
GET /{id}/lines/{lineId}/receipts
POST /{id}/receipts/{invHistId}/cancel
적치지시 탭 2개. 지시 등록 — 입고건(주문) 단위 마스터-디테일. 상단에서 입고건을 고르고 [이 입고 전체 지시] 한 번으로 그 입고의 미지시 배치를 전략으로 일괄 배정(용량 부족 시 1:N 분할)해 확인 후 발행한다. 물건이 트럭 단위로 들어와 한 자리에 내려지므로 지시도 그 단위로 거는 것. 하단 (라인, Lot) 배치는 전략이 배정하지 못한 건을 수동 지시할 때 쓴다. 생성 시 스테이징 재고를 예약(aloc)한다.
지시 관리 — 지시 목록 조회 / 취소(실행 실적이 없는 건만). 재배정은 취소 후 재지시로 갈음		 구현 GET /inbound/putaway/lines
POST /inbound/putaway/tasks/preview
POST /inbound/putaway/tasks
GET /inbound/putaway/tasks
POST /tasks/{id}/cancel
적치 상품 단위 마스터-디테일. 작업자가 스테이징에서 집어 드는 단위가 상품이라 상단은 상품별 집계(지시 건수 · 로케이션 수 · 잔여), 하단은 그 상품이 어느 로케이션에 얼마씩 가는지다 — 1:N 분할을 한눈에 보고 한 번 들고 나가 나눠 넣게 하려는 배치. [전량 적치]가 주 동선이고 건별 부분 실행은 하단 패널이 맡는다. 지시받은 로케이션으로만 적치할 수 있다 — 다른 곳에 두려면 취소 후 재지시(실적 로케이션 수정은 두지 않기로 결정) 구현 GET /inbound/putaway/tasks
POST /tasks/{id}/execute
POST /tasks/execute(일괄)
/lines/{id}/candidate-locs(수동 지시용)
입고확정 입고 흐름의 마지막 단계. 라인별 예정/검수/적치/결품 수량을 보여주고, 결품(expctQty − rcvdQty) 사유 입력 후 확정 → RECEIVING → COMPLETED.
선행 조건: 전 라인 미적치 잔량 0 — 미적치가 남으면 확정 버튼 비활성 + 사유 표시(검수만 하고 확정하는 것은 업무적으로 성립하지 않음)		 미구현 POST /{id}/close 존재하나 의미가 달라 재작성 필요 (현재는 RECEIVING→RECEIVED 중간 전이)

3. 재고 (Inventory)

화면주요 기능상태API
현재고 조회 상품 + 로케이션 + Lot 단위 스냅샷. 가용재고(onHand − aloc − hld) 파생 컬럼, 유통기한 임박 강조 구현 GET /inventory/stock
재고 이력 조회 RECEIVE / MOVE / ADJUST / PICK / SHIP 원장. 참조문서번호로 입·출고 역추적 구현 GET /inventory/history
재고 속성변경 Lot의 제조일자/유통기한 정정 — 수량이 아닌 속성만 고친다. 재고를 한 톨도 움직이지 않는 유일한 처리 화면(inv·inv_hist 무변경)이라 정정의 원장은 lot_attr_chng 하나다. 제조일자는 배치 재사용 키(상품+입고일자+제조일자)의 일부라 다른 Lot과의 충돌을 서버가 막는다(uq_lot은 (prod_id, lot_no)에만 걸려 DB가 안 잡는다). 유통기한 미관리 상품의 Lot은 대상 아님. (재고상태 전환은 재고 보류, 수량 정정은 재고조사) 구현 GET·PUT /inventory/lot-attrs
재고 보류 특정 재고(상품+로케이션+Lot)의 일부/전량을 수량 단위로 보류해 가용재고에서 제외(inv.hld_qty — 재고상태 컬럼 아님). 등록/해제 각각 사유(공통코드, 기타 시 텍스트) 기록, 부분 해제 허용, 실적 2테이블 append-only 보존. 유통기한 만료 Lot 자동 보류(배치)는 백로그 구현 POST /inventory/holds · GET /inventory/holds · POST /inventory/holds/{id}/release · GET /inventory/holds/acrsts · /rlz-acrsts
재고조사 (실사) 조사 대상 지정(존/로케이션/상품 범위) → 라인별 전산수량 스냅샷 → 실사수량·사유 입력 → 확정 시 차이를 ADJUST로 보정. 재고 수량 정정의 유일한 경로(건별 조정 화면 없음 — 재고 하나만 고치려면 범위를 좁게 잡는다). 조정수량 = 실사수량 − 확정시점 전산수량이라 확정 후 전산수량은 실사수량과 정확히 일치한다(확정이 재고 행 락을 걸고 다시 읽는다). 차이 0 라인은 이력·사유 없음, 미입력(NULL)은 「미조사」로 건너뜀. 장부에 없는 재고는 라인 수동 추가로 등록(기초재고·발견재고 — Lot은 기존 것만). 실적 테이블 없음 — 조정실적 조회는 재고 이력 조회에서 조사번호로 구현 POST·GET /inventory/stocktakes
GET·PUT·POST /inventory/stocktakes/{id}/lines
POST /inventory/stocktakes/{id}/confirm · /cancel · /resync
재고 이동 보관 ↔ 보관 이동을 2단계(지시=예약 → 확정=실물 MOVE)로 처리. 메뉴는 하나, 화면 안 탭 2개 — ① 이동지시등록: 현재고에서 대상 선택 → TO·수량 담기 → 일괄 등록 시 inv.aloc_qty 선점(예약 — aloc_qty는 예약수량 일반), 온도대·적재가능수량(max_qty − 현재고 − 미완료 지시 유입 잔량) 검증. ② 이동지시 관리: 지시 목록, 확정(부분 허용 — inv_hist MOVE 2행 + 예약 소진, 전량 시 DONE), 취소(잔량 예약 해제 — 실적 없으면 CANCELLED, 부분확정 후면 지시수량 차감 후 DONE). 확정·취소는 이동구분(mov_dvsn)이 재고이동(INV_MOV)인 지시만 — 적치·피킹 유형은 각자의 화면 전용. 실적 테이블 없음 — 실적 조회는 재고 이력 조회로 수렴 구현 POST·GET /inventory/moves
POST /inventory/moves/{id}/confirm
POST /inventory/moves/{id}/cancel

4. 출고 (Outbound)

화면주요 기능상태API
출고예정 목록 검색(출고번호/상태/출고유형/차량편수/출고예정일), 헤더–라인 2단 구조. 등록·취소 기능 없음 — 조회 전용이다(2026-08-04 확정). 출고주문은 OMS 출고주문 확정으로만 생성되고 확정취소로만 사라진다(입고예정 ASN과 같은 구조). 이 화면을 프로세스 화면(생성/취소)으로 규정한 참고 설계는 따르지 않는다 — 창고가 예정을 스스로 만들거나 없애면 「주문은 확정인데 창고엔 아무것도 없는」 상태가 고착된다. 기능 누락이 아니므로 되살리지 말 것.
입고예정에 없는 컬럼이 둘이다 — 웨이브(편성된 웨이브번호 + 편입 출처, 비어 있으면 미편성)와 할당 진행/할당수량. 뒤엣것은 저장 컬럼이 아니라 outb_alloc 집계다(할당 수량을 라인에 두지 않는 원칙). 라인의 잔량은 「아직 못 채운 부분할당」이라 음수가 나지 않는다 — 과입고가 가능한 입고 잔량과 갈리는 지점		 구현 GET /outbound/orders
/{id}/lines
/outbound/order
웨이브 편성 좌: 웨이브 목록(선택 = 작업 대상) / 우 상: 미편성 주문 · 우 하: 웨이브 소속 주문. 담기(↓)·빼기(↑)·해체.
웨이브 = 피킹지시 발행 단위 — 여러 주문을 묶어 한 번에 집품 지시를 내기 위한 그룹
전략 편성이 같은 화면에 있다 — 전략을 하나 골라 선택실행하거나 비워서 전 전략 자동실행(우선순위 순, 앞 전략이 주문을 선점). 실행 전 미리보기로 주문별 판정 근거를 조건 단위까지 볼 수 있고(DB 변경 없음), 실행 후에는 전략별로 「웨이브를 만들었는지 / 왜 안 만들었는지」를 보여준다. 편입 0건이면 웨이브를 만들지 않으므로 재실행해도 빈 웨이브가 쌓이지 않는다.
미리보기·실행 결과는 모달이다 — 카드 안에 펼치면 그 높이만큼 아래 그리드 3개가 눌린다. 같은 이유로 웨이브 목록을 좌측 컬럼으로 세워 세로를 통째로 쓰게 하고, 컬럼이 많은 주문 그리드 둘이 남은 폭을 쓰며 세로를 반씩 나눈다. 웨이브 목록은 다른 그리드와 같은 단일 행이고, 좁은 폭에서 뒤쪽 일자 컬럼이 가로 스크롤로 밀리므로 고를 때 필요한 셋(번호·상태·생성 전략)을 앞에 둔다.
