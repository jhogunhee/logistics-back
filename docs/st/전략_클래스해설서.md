# 전략 시스템 클래스 해설서

`com.project.wmsback.strategy` 패키지의 클래스별 역할과 책임을 전체 틀 속에서 설명한다.
설계의 "왜"는 `전략시스템_재설계안.md`(§3 상단의 2026-08-02 커널 축소 결정 포함), 실행 흐름의
업무 정의는 `전략_프로세스정의서.md`, 테이블·JSON 구조는 `전략_테이블설계서.md`를 참조.
이 문서는 **코드를 읽기 위한 지도**다.

---

## 1. 전체 틀 — 이 시스템이 답하는 세 가지 질문

전략 시스템의 모든 클래스는 아래 세 질문 중 하나에 속한다. 이 틀만 잡으면 어떤 클래스를 만나도 위치를 찾을 수 있다.

```
① 메타 (화면에 뭘 보여줄까)        ② 정의 관리 (저장·검증·이력)        ③ 실행 (저장된 정의를 평가)
   선택 가능한 규칙·방식·조건필드      관리자가 조립한 정의(JSON)를          입고 시점에 정의를 읽어
   목록을 enum에서 뽑아 내려준다       검증해서 저장하고 이력을 남긴다        추천/차단을 판정한다
```

셋을 관통하는 설계 사상은 하나다. "공통코드로 아무거나 등록되지만 실제로 동작하는지는
아무도 보장하지 않는" 구조를 만들지 않는 것:

- **P1** — 화면 선택지는 반드시 코드(enum)에서만 나온다. DB에 뭘 등록해서 옵션을 만드는 경로 자체가 없다.
- **P2** — 저장 시점에 전부 검증한다. "저장은 되는데 실행하면 터지는" 정의를 원천 차단한다.
- **P4** — 미리보기와 실전이 같은 산정 함수를 쓴다.
- 실행 코드 곳곳의 `IllegalStateException`은 "P2를 통과한 정의라면 불가능한 상태"라는 뜻이다
  (= 정의/배포 불일치, 운영 알람 대상).

구성요소(검수 규칙·적치 방식)의 표현 방식은 **enum**이다: `name()`이 DB에 저장되는 code이고,
상수가 표시명·설명·판정 로직·파라미터 검증을 전부 가진다. 상수 추가 = 메타 API(화면 선택지)·
저장 검증·실행에 동시 반영이며, 처리 누락은 컴파일 에러로 드러난다.
(1차 구현의 Descriptor/레지스트리 커널은 2026-08-02에 이 방식으로 축소 — 재설계안 §3 참조.)

패키지는 3개다.

| 패키지 | 성격 |
|---|---|
| `core` | 두 도메인이 공유하는 부품 — 조건 DSL, 리비전, 실행로그, 메타 API |
| `inspection` | 검수 정책 — 입고 저장 직전 규칙을 평가해서 **차단** (전역 1개 정책) |
| `putaway` | 적치 전략 — 입고 후 어느 로케이션에 둘지 **추천** (여러 전략 중 조건 매칭으로 선택) |

## 2. core — 공통 부품

### 2-1. 조건 DSL (`condition`) — "적용대상" 같은 필터의 문법

관리자가 "온도대 = 냉장 AND 벤더 IN (A, B)"처럼 조건을 조립할 수 있게 하는 부품.

| 클래스 | 역할 |
|---|---|
| `FieldCondition` | 조건 1건 = `{필드, 연산자, 값들}`. JSONB 컬럼(`line_cond`·`loc_cond`)에 배열로 저장되고 **배열 원소끼리는 항상 AND**. 적치의 적용대상은 조건 배열이 아니라 `odr_dvsn` 스칼라다 (§3-1) |
| `ConditionOperator` | EQ/NE/IN/NOT_IN/GE/LE/BETWEEN/LIKE. 연산자가 "값 몇 개 필요한지"(`minVals`/`maxVals`)와 "실제 판정"(`test(실제값, 조건값들)`)을 자기가 가진다. 실제값 null이면 부정 연산자(NE·NOT_IN)만 참. GE/LE/BETWEEN은 문자열 사전순 비교 — ISO 일자처럼 사전순=값순인 필드에만 허용할 것 |
| `ConditionField<T>` | "조건을 걸 수 있는 필드"의 규약. 라벨, 허용 연산자, 값 선택지 출처(`optionSource`), **판정 대상 T에서 실제값을 뽑는 방법**(`extract`)을 필드가 안다. 도메인별 enum이 구현 |
| `ConditionEvaluator` | 함수 두 개뿐. `validate`(저장 시: 필드 실존? 연산자 허용? 값 개수?) + `matchesAll`(실행 시: 전부 AND 판정, 빈 목록 = 무조건 참). **저장 검증과 실행 판정이 같은 필드 맵(BY_CODE)을 쓰므로 어긋날 수 없다** |
| `SortCriterion` | 정렬 기준 1건 `{필드, ASC/DESC}`. 적치의 `loc_srt`에 사용 |

### 2-2. 이력 (`entity` + `service`) — 감사의 두 축

| 클래스 | 역할 |
|---|---|
| `StgyRvsn` + `StgyRvsnService` | **"정의가 어떻게 바뀌어 왔나."** 저장할 때마다 정의 전체를 JSON 스냅샷으로 **같은 트랜잭션에서** 기록. **조회 전용 감사 이력**이다 — 복원 흐름은 없다(2026-08-02 제거). 예전 정의로 되돌리려면 스냅샷 JSON을 보고 편집 화면에서 다시 저장한다. 전략이 삭제돼도 스냅샷 행은 DB에 남는다 |
| `StgyExecLog` + `StgyExecLogService` | **"실행 시점에 무슨 판단을 했나."** 전략 id + 리비전 + 대상 문서(`tgt_ref`) + 한 줄 요약(`rslt_smry`) + 판정 상세 JSON(`dcsn_trc`). 기록이 `REQUIRES_NEW`인 이유: 검수 위반이면 입고 저장 트랜잭션이 롤백되는데 **"위반이라 차단했다"는 기록은 살아남아야** 한다. 로그 직렬화 실패는 업무를 막지 않는다(경고만) |
| `StgyTyp` (INSP/PTAWY + 2차 선반영 WAV·ALOC), `TrgrTyp` (MANUAL/AUTO/PREVIEW — AUTO는 2차 웨이브용, PREVIEW는 1차 미기록) | 위 두 테이블이 도메인 공용이라 쓰는 구분자 enum. DB CHECK(`ck_stgy_rvsn_typ` 등)와 값을 맞춘다 |

`stgy_exec_log.rvsn_no` × `stgy_rvsn` 조합으로 "그때 그 판정이 어떤 정의로 내려졌는지" 재구성 가능 (P5).

### 2-3. 메타 API (`controller` + `StrategyOptionService`)

| 클래스 | 역할 |
|---|---|
| `StrategyMetaController` | 화면 폼 렌더링에 필요한 전부를 내려주는 4개 GET: 검수 규칙 목록(`InspectionRule` enum), 적치 방식 목록(`PutawayMethod` enum), 조건 필드 목록(`fields/{domain}` — 필드 enum), 값 선택지(`options/{source}`) |
| `StrategyOptionService` | `optionSource` 문자열("vendors", "bizDvsns"…)을 기준정보 조회로 바꾸는 switch. 조건값 드롭다운의 내용물 |
| `StrategyExecLogController` | 실행로그 조회 API |
| `ComponentResponse` | 규칙·방식 선택지 응답 `{code, name, description, deprecated}` — enum을 직렬화한 것 |
| `FieldDescriptorResponse` / `OptionResponse` / `RvsnResponse` / `ExecLogResponse` | 나머지 API의 응답 포장지 |

## 3. putaway — 적치 전략 (추천)

### 3-1. 정의 쪽 (②)

| 클래스 | 역할 |
|---|---|
| `PtawyStgy` (entity, 헤더) | 전략 1개. `odrDvsn`(적용대상 발주구분 — NULL = 전체, 유형당 1개 UNIQUE라 우선순위 컬럼 없음), `untSpltYn`(입수 단위 절사), `locSrt`(정렬 기준), `lastRvsnNo`, 단계 목록 소유. 선택 규칙: 입고의 발주구분 일치 → 전체 → 수동 폴백 |
| `PtawyStgyStg` (entity, 단계) | **적치 전략의 핵심 개념.** "1단계: 같은 상품에 합치기 → 2단계: 빈 로케이션 → 3단계: 아무데나"를 관리자가 drag&drop으로 배열한 순서(`srtSeq`)대로 시도. 단계 = 방식 code(`mthdCd` — `PutawayMethod` enum name) + 파라미터(`mthdPara` — 현재 방식들은 전부 파라미터 없음) + **조건**(`lineCond` — 이 조건일 때만 이 단계 적용) + **적치위치 지정**(`locCond` — 존 업무유형 IN 최대 1건, 조건이 아니라 적용기준값) |
| `PtawyStgyDefinition` (record) | 전략 정의의 순수 데이터 형태. **저장 요청 본문이자 리비전 스냅샷의 형태** — 같은 모양이라 복원 = 재저장 |
| `PtawyStgyService` | CRUD + 리비전 기록. 핵심은 `validate`: 적용대상(전체/정상/긴급만 — 반품 스코프 아웃), 방식 code 실존(`PutawayMethod.find`)·비은퇴, 파라미터 없음 확인, 단계 조건, 적치위치 지정 형태(BIZ_DVSN IN 1건), 정렬 기준까지 **저장 전에 전부 검사** (P2의 관문). `requireVacant`가 유형당 1개를 친절한 메시지로 선검사(DB UNIQUE가 최종 방어) |
| `PtawyStgyController` | REST: CRUD + 미리보기 2종(미저장 정의 `/preview`, 저장본 `/{id}/preview`) + 리비전 조회(전용) |
| `PtawyStgyResponse` / `PtawyStgySummaryResponse` / `PtawyPreviewRequest` / `PutawayRecommendRequest` / `PutawayRecommendResponse` | 요청/응답 포장지 (뒤 둘은 실행 쪽 추천 API용) |

### 3-2. 실행 쪽 (③) — 추천 흐름 순서대로

작업자가 "이 입고 라인 100개 어디 둘까?"를 물으면:

1. **`PutawayRecommendService.recommend`** — 진입점은 전략 패키지가 아니라 inbound의
   `PutawayController`(`POST /putaway/lines/{ibLineId}/recommend`)다. 입고 라인에서 상품·벤더를 뽑아
   `PutawayTarget`(단계 조건의 판정 대상)을 만들고 전략을 선택한다: `ib_order.odrDvsn` 일치 전략 →
   전체(`odrDvsn` NULL) 전략. 유형당 1개(UNIQUE)라 우선순위 없이 결정적이다. 전략 미설정이면
   `strategySelected=false`로 응답하고 화면이 수동 후보로 폴백한다.
2. **`PutawayQueryRepository.storageStocks`** — 후보 모집단을 한 방 쿼리로: **상품 온도대 일치 +
   STORAGE 로케이션** 전체의 (점유수량, 같은 상품 보유 여부, 존 업무유형). 온도대·STORAGE가
   조건 DSL에 없는 이유 — 조건이 아니라 **모든 단계의 불변 전제**라서 쿼리에서 강제한다.
3. **`PutawayMethodContext`** (record) — 모집단을 방식에게 넘기는 봉투. 내부 record `LocStock`
   (로케이션 + 점유량 + 같은상품유무 + 존업무유형)은 로케이션 조건(`PutawayLocField`)의 판정 대상이기도 하다.
4. **`PutawayMethod`** (enum) — **후보를 "고르기만"** 한다. `SAME_PROD_LOC`(적재로케이션 — 같은 상품
   재고가 있는 곳), `EMPTY_LOC`(빈로케이션), `ANY_LOC`(전체 보관). 각 상수의 `candidates(ctx)`가
   판정 로직이고 사실상 한 줄이다 — 조건 필터·정렬·수량 분할은 방식 책임이 아니라 서비스 책임.
   `find(code)`는 저장 검증용(없으면 empty), `of(code)`는 실행용(없으면 정의/배포 불일치 예외).
5. **`PutawayRecommendService.compute`** — 산정 본체 (프로세스정의서 §3.3). 단계 순서대로:
   잔여수량 0이면 SKIP → `lineCond` 게이트 → 방식이 후보 선정 → `locCond` 필터 → `locSrt` 정렬
   (빈 목록 = 피킹순위 ASC → 로케이션코드 ASC, 끝에 id를 붙여 항상 결정적) →
   로케이션마다 "적재가능 = max_qty − 점유 − 이번에 이미 배정한 분" 계산(`max_qty` NULL은 스키마상
   없어야 하지만 라이브 불일치 대비 무제한으로 다루고 trace에 경고), `untSpltYn`이면 입수 배수로 절사,
   배정 후 잔여 차감. 전 과정을 `trace`(JSON)로 남겨 실행로그·미리보기의 "왜 이렇게 추천됐나"에 쓴다.
6. **`PutawayTarget`** (record) — 단계 조건의 판정 대상 (상품 + 벤더코드).
7. **`PutawayTargetField`** (enum: TMP_ZON·VNDR·PROD·INB_UOM — 단계 조건용) / **`PutawayLocField`**
   (enum: BIZ_DVSN 하나, 연산자 IN — 적치위치 지정용) — **상수 추가 = 화면 자동 노출.**

`preview`는 같은 `compute`를 미저장 정의로 돌릴 뿐이다(DB 변경·로그 없음 — P4). 유형 매칭 선택이라
"실제 선택될 전략" 비교·경고는 없다 (편집 중 전략이 곧 그 유형의 전략이다).

주의: **전략은 추천만 한다.** 실행(즉시 MOVE)은 기존 `PutawayService`(inbound 패키지)가 담당하고,
추천~실행 사이의 재고 변동은 실행 측 가드가 최종 방어한다 (추천은 예약이 아니다).

## 4. inspection — 검수 정책 (차단)

적치와 대칭이지만 두 가지가 다르다: **정책이 전역 1개**(선택 로직 없음)이고,
**전 규칙을 AND 실행해서 위반이면 입고 저장 자체를 거부**한다.

| 클래스 | 역할 |
|---|---|
| `InspPlcy` (entity, 헤더) | 정책 1행 (전역 1개 강제는 서비스에서 — D8). `prty`가 없는 게 의도: 선택되는 전략이 아니라 전량 실행 유형이라, 있으면 화면·스키마가 거짓말을 하게 된다 |
| `InspPlcyRule` (entity) | 정책에 붙은 규칙 1건 = `ruleCd`(`InspectionRule` enum name) + `para`(JSONB — 저장 시 `validatePara`를 통과한 값만). 같은 규칙 중복 등록은 UNIQUE(`uq_insp_plcy_rule`)로 차단. `srtSeq`는 표시·위반 목록 정렬용(전 규칙 실행이라 결과엔 무관) |
| `InspPlcyDefinition` (record) | 정의의 순수 데이터 형태 (저장 본문 = 스냅샷 형태) |
| `InspPlcyService` | CRUD·저장 검증·리비전·전역 1행 강제 + 미리보기(`preview` — 미저장 정의를 로트 목록에 평가, `evaluateOne` 공용이라 P4). 적치의 `PtawyStgyService`와 같은 위치. 검증: rule_cd 실존·비은퇴·중복 금지 + `rule.validatePara(para)` |
| `InspPlcyController` | REST: CRUD + 미리보기(`/preview`) + 리비전 조회. 정책이 전역 1개라 경로에 id가 없다 |
| `InspectionService` | 실행부. `checkReceive`가 **`ReceivingService.receive`(입고 검수 저장) 직전 훅**으로 호출된다. 정책 없음/규칙 0건이면 통과(검수 자체를 막지 않는다). 라인마다 `evaluateOne`으로 전 규칙 평가 → 실행로그 기록(REQUIRES_NEW) → 위반 있으면 `InspectionViolationException`으로 저장 전체 롤백. `evaluateOne`은 실행·미리보기 공용 (P4) |
| `InspectionRule` (enum) | **검수 규칙의 전부가 이 한 파일에 있다.** 상수마다 세 가지를 가진다: `validatePara`(저장 시 파라미터 검증·정규화 — P2), `skipReason`(이 상품엔 해당 없음 — 예: 유통기한 미관리), `check`(위반이면 `Violation`). `SHELF_LIFE_PCT`(유통기한 잔여비율 — `minPercent` 0~100 필수), `LOT_DATE_REVERSE`(역순제한 — `excludeSameDay` 기본 true). 파일 하단의 정적 헬퍼들이 파라미터 변환을 공통 처리한다 |
| `InspectionContext` (record) | 규칙 평가 입력 (상품, 입고일, 제조일). `InspectionQueryRepository`를 들고 다녀서 규칙이 리포지토리를 직접 주입받지 않는다 — 순수 함수에 가깝게 유지 |
| `InspectionQueryRepository` | 규칙이 쓰는 조회 포트: "이 상품의 보유 재고(on_hand>0) 중 최신 제조일자" |
| `Violation` / `InspRuleResult` | 판정 결과 (메시지, 실제값, 기댓값 / pass·skip·violation) |
| `InspPlcyResponse` / `InspPreviewRequest` / `InspPreviewResponse` | 요청/응답 포장지 |
| `InspectionViolationException` | 라인별 위반 목록을 담은 예외. `GlobalExceptionHandler`를 거쳐 화면에 구조화되어 내려간다 |

## 5. wave — 웨이브 전략 (편성)

적치·검수와 달리 **구성요소 enum이 없다.** 고를 실행기가 없고 조건만 있는 유형이라
`PutawayMethod`·`InspectionRule`에 해당하는 파일이 아예 없고, 정의의 전부가 조건그룹이다.

| 클래스 | 역할 |
|---|---|
| `WavStgy` (entity) | 전략 1행. `condGrp`가 **`List<List<FieldCondition>>` JSONB** — 바깥이 그룹(OR), 안이 조건(AND). 하위 테이블이 없어 웨이브 도메인은 테이블 1개로 끝난다. `prty`는 실행 순서이자 **선점 순서**다(적치처럼 지우면 안 된다 — §10.1 설계서) |
| `WavStgyDefinition` (record) | 정의의 순수 데이터 형태 (저장 본문 = 스냅샷 형태) |
| `WavStgyService` | CRUD·저장 검증·리비전. 검증의 핵심은 **빈 그룹 거부** — 조건 0건 그룹은 「무조건 참」이라 미편성 주문 전부를 쓸어담는데, DB CHECK는 바깥 배열 길이만 보므로 `[[]]`가 통과한다. 여기가 유일한 방어선 |
| `WaveOrderField` (enum) | 조건 필드의 전부: `OUTB_TYP`(출고유형 — 일반/반품) · `VHCL_FLTNO`(차량편수 — 1편·2편…). 둘 다 값 목록을 공통코드가 소유해 optionSource(`outbTyps`·`vhclFltnos`)가 코드관리 화면과 자동으로 맞는다. **등가 연산자만** 연다(사전순 비교라 `"10" < "2"`). 납품처그룹·납품처유형은 `store`에 컬럼이 없어 보류 |
| `WaveOrderTarget` (record) | 판정 대상 = 주문 1건의 값 스냅샷. 엔티티가 아니라 값으로 뽑아 판정을 순수 함수로 유지한다. 판정에 쓰이는 건 `outbTyp`·`vhclFltno` 둘뿐이고 나머지는 화면·로그 표시용 |
| `WaveMatcher` (static) | **판정의 전부.** 그룹 OR / 조건 AND를 평가하면서 동시에 조건 단위 근거(trace)를 만든다. 첫 통과 그룹에서 멈추지 않는 이유는 "2번 그룹은 왜 안 걸렸나"를 화면이 보여줘야 하기 때문 |
| `WaveStgyExecService` | 실행(`execute`)과 미리보기(`preview`)가 같은 `WaveMatcher`를 공유(P4). 실행은 전략을 `prty` 순으로 돌며 웨이브 생성 + 주문 편입, **편입 0건이면 웨이브를 만들지 않는다**(= 재실행 안전장치). 편입된 주문은 후보 목록에서 빠져 뒤 전략이 못 가져간다 |
| `WaveMatchResult` (record) | 주문 1건의 판정 결과 + 그룹·조건별 trace. **미리보기 응답이자 실행로그 `dcsn_trc`의 원소** — 화면이 한 컴포넌트로 둘 다 그린다 |
| `WavStgyController` | REST: CRUD + 미리보기 + 리비전. **실행은 여기 없다** — `OutbWaveController`의 `POST /outbound/waves/stgy-exec`(업무 도메인) |
| `OutbOrder.assignWave(wave, regTyp)` | 편성의 실체. 중복 편성 거부가 곧 선점 규칙이고, `wavRegTyp`(STGY/MANUAL)이 수동 편성을 가시화한다. `unassignWave()`가 둘을 함께 비우는 것이 `ck_outb_order_wav_reg`를 지키는 지점 |

## 7. 한 장 요약

```
[화면]  ComponentPicker·RuleParamForm·ConditionBuilder
           ↑ ①메타: StrategyMetaController ← InspectionRule·PutawayMethod·필드 enum + OptionService
[저장]  Definition(JSON) → PtawyStgyService/InspPlcyService.validate
           (enum.find + rule.validatePara + ConditionEvaluator.validate)  ← P2: 여기서 다 걸러짐
        → entity 저장 + StgyRvsnService.snapshot (같은 트랜잭션)
[실행]  적치: recommend → 전략선택(발주구분 일치 → 전체) → QueryRepository(불변전제) → 단계 loop
              [lineCond 게이트 → PutawayMethod.of(코드).candidates → locCond(위치지정)필터 → locSrt정렬 → 수량배정] → trace
        검수: checkReceive → 전 규칙 AND [rule.skipReason → rule.check] → 위반시 예외(롤백), 로그는 생존(REQUIRES_NEW)
        웨이브: stgy-exec → 전략 prty순 loop [WaveMatcher(그룹 OR/조건 AND) → 편입 0건이면 웨이브 미생성]
                → 편입분은 후보에서 제거(선점) → trace
        미리보기 = 같은 함수, 로그만 없음 (P4)
```

**추천 독서 순서**: `PutawayRecommendService.compute`(적치의 전부가 한 함수에 있다) →
`PutawayMethod`·`InspectionRule` enum(구성요소의 전부) → `PtawyStgyService.validate`(저장 검증) →
`InspectionService.checkReceive`(검수 훅) → `WaveMatcher` + `WaveStgyExecService.execute`
(웨이브는 이 둘이 전부다) — 이 다섯을 따라가면 전체가 잡힌다.
