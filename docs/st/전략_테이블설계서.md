# 전략 시스템 테이블 설계서 — 1차: 검수 제약 · 적치 전략 / 2차: 웨이브 전략

> 작성일: 2026-08-02 (2차 증보 2026-08-03)
> 범위: **신설 7개 테이블** (공용 2 + 검수 2 + 적치 2 + **웨이브 1**) + 기존 2개 테이블 컬럼 추가.
> 할당 테이블(`aloc_stgy`, `aloc_stgy_slot`)은 3차 — 전체 구도는 `전략_테이블설계안.md` 참고.
> **2차(웨이브) 상세는 §10.**
> 규칙: `docs/schema.sql`이 스키마의 주인 · FK 0건(참조 무결성은 애플리케이션) · 감사 컬럼 4종 전 테이블 공통 · 네이밍은 `docs/naming-dictionary.md` (신규 15단어 등재 선행) · 사용여부 컬럼 없음(D4).
>
> **1차 제외**: `putaway_task` 연결 컬럼(`ptawy_stgy_id`·`rvsn_no`) 추가는 보류한다 — 이 테이블은 스키마에만 있고 현행 코드가 쓰지 않는다(적치는 지시 없이 즉시 MOVE). 추천 실행의 추적은 `stgy_exec_log`가 담당하고, 지시 기반 전환 시 함께 추가한다.

## 1. ERD (텍스트)

```
insp_plcy 1 ──── N insp_plcy_rule            (insp_plcy_id 느슨한 참조)
ptawy_stgy 1 ─── N ptawy_stgy_stg            (ptawy_stgy_id 느슨한 참조)
wav_stgy   1 ─── N outb_wave                 (outb_wave.wav_stgy_id 느슨한 참조 — 실행 산출물)

stgy_rvsn      N ──── 1 (stgy_typ, stgy_id)  → insp_plcy · ptawy_stgy · wav_stgy (다형 느슨한 참조)
stgy_exec_log  N ──── 1 (stgy_typ, stgy_id)  → 〃        · tgt_ref → ib_order.ib_no / outb_wave.wav_no (표시용)
```

FK는 없다. `stgy_rvsn`·`stgy_exec_log`의 (stgy_typ, stgy_id)는 원본 전략이 **삭제된 뒤에도 남는** 느슨한 참조다 (inv_hist.rfn_doc_no와 같은 성격) — 삭제 후 이력 조회·복원의 근거가 된다.

## 2. stgy_rvsn — 전략 리비전 스냅샷 (공용)

전략 저장(생성·수정·복원)마다 정의 전체를 JSON으로 남기는 append-only 이력. `created_at`/`created_by`가 곧 저장 시각/저장자다.

| 컬럼 | 타입 | NULL | 기본값 | 설명 |
|---|---|---|---|---|
| `stgy_rvsn_id` | BIGINT IDENTITY | NN | | PK |
| `stgy_typ` | VARCHAR(10) | NN | | 전략 유형. `INSP` 검수 / `PTAWY` 적치 / `WAV` 웨이브 (3차: `ALOC`) |
| `stgy_id` | BIGINT | NN | | 유형별 헤더 PK (insp_plcy_id · ptawy_stgy_id · wav_stgy_id). FK 없음 |
| `rvsn_no` | BIGINT | NN | | 전략별 1부터 증가. 헤더의 `last_rvsn_no`가 최신값을 가리킨다 |
| `snpsht` | JSONB | NN | | 정의 전체 스냅샷 — 구조는 §8.1 |
| 감사 4종 | | | | `created_*` = 저장 시각/저장자. append-only라 `updated_*`는 항상 NULL |

제약·인덱스:

```sql
CONSTRAINT uq_stgy_rvsn UNIQUE (stgy_typ, stgy_id, rvsn_no)
CONSTRAINT ck_stgy_rvsn_typ CHECK (stgy_typ IN ('INSP','PTAWY','WAV','ALOC'))
CONSTRAINT ck_stgy_rvsn_no CHECK (rvsn_no >= 1)
```

- CHECK의 값 목록에 `WAV`·`ALOC`을 미리 포함해 뒀다 — 2차(웨이브)가 DDL 변경 없이 그대로 썼다. 유형 추가는 CHECK 수정이 필요한 구조적 enum이다(status 류와 동일한 취급).
- 리비전 부여는 헤더 행 잠금 하에서 `last_rvsn_no + 1` — 동시 수정 직렬화. `uq_stgy_rvsn`이 최후 방어선.

## 3. stgy_exec_log — 전략 실행 로그 (공용)

실행·미리보기의 결과와 건별 판정 근거. 검수처럼 결과 행이 없는 유형(산출물=차단 예외)의 유일한 실행 흔적이다.

| 컬럼 | 타입 | NULL | 기본값 | 설명 |
|---|---|---|---|---|
| `stgy_exec_log_id` | BIGINT IDENTITY | NN | | PK |
| `stgy_typ` | VARCHAR(10) | NN | | `INSP` / `PTAWY` / `WAV` (3차: `ALOC`) |
| `stgy_id` | BIGINT | NN | | 실행에 사용된 전략. 삭제 후에도 남는 느슨한 참조 |
| `rvsn_no` | BIGINT | NN | | 실행에 사용된 리비전 — `stgy_rvsn`과 조합해 "그때의 정의"를 재구성 |
| `trgr_typ` | VARCHAR(10) | NN | | `MANUAL` 화면 조작 / `AUTO` 자동 / `PREVIEW` 미리보기. **현재 코드가 쓰는 값은 `MANUAL`뿐이다** — 웨이브 전략 실행도 화면 조작이라 MANUAL이고, `AUTO`는 스케줄 실행이 생길 때를 위한 선반영 |
| `tgt_ref` | VARCHAR(30) | NULL | | 대상 문서 번호 (입고번호 IB-… / 웨이브번호 WV-…). 가상 입력 미리보기와 「편입 0건이라 웨이브를 만들지 않은」 웨이브 실행은 NULL. 새 컬럼이므로 `ref` 표기(rfn 아님 — 사전 결정) |
| `rslt_smry` | VARCHAR(200) | NULL | | 사람용 한 줄 요약. 예: "라인 3건 중 위반 1건" |
| `dcsn_trc` | JSONB | NULL | | 건별 판정 상세 — 구조는 §8.2 |
| 감사 4종 | | | | `created_at` = 실행 시각 |

제약·인덱스:

```sql
CONSTRAINT ck_stgy_exec_log_typ  CHECK (stgy_typ IN ('INSP','PTAWY','WAV','ALOC'))
CONSTRAINT ck_stgy_exec_log_trgr CHECK (trgr_typ IN ('MANUAL','AUTO','PREVIEW'))
CREATE INDEX ix_stgy_exec_log_stgy ON stgy_exec_log (stgy_typ, stgy_id, created_at);
CREATE INDEX ix_stgy_exec_log_ref  ON stgy_exec_log (tgt_ref);
```

- 검수 위반(=검수 저장 롤백) 시에도 로그는 남아야 하므로 기록은 별도 트랜잭션(REQUIRES_NEW)이다.
- PREVIEW는 기록하지 않는다(코드에서 미호출 — 용량·소음 관리). 컬럼·CHECK는 선반영.
- 보존 기간 정책(오래된 로그 삭제 배치)은 운영 단계 결정 사항 — 테이블 설계에는 반영하지 않는다.

| 컬럼 | 타입 | NULL | 기본값 | 설명 |

## 6. ptawy_stgy — 적치 전략 헤더

> **[2026-08-03 개정]** `prty`·`tgt_cond`는 **제거**됐다 (migration-putaway-stgy-odr-dvsn.sql) —
> 적용대상은 `odr_dvsn VARCHAR(10) NULL`(공통코드 ODR_DVSN, NULL = 전체) 단일 선택이고,
> `ux_ptawy_stgy_odr_dvsn UNIQUE (COALESCE(odr_dvsn,'ALL'))`가 유형당 1개를 강제해 우선순위를 대체한다.
> 선택 규칙: ib_order.odr_dvsn 일치 → 전체 → 수동 폴백. ib_order에도 odr_dvsn이 신설됐다(확정 시 복사).
> 아래 표의 `prty`·`tgt_cond` 행은 원안 기록이다. `loc_cond`(§7)는 "적치위치 지정 — BIZ_DVSN IN 최대 1건"으로 의미가 좁아졌다.

| 컬럼 | 타입 | NULL | 기본값 | 설명 |
|---|---|---|---|---|
| `ptawy_stgy_id` | BIGINT IDENTITY | NN | | PK |
| `stgy_nm` | VARCHAR(100) | NN | | 전략명 (표시용) |
| `prty` | INTEGER | NN | 0 | (제거됨 — 개정 노트 참조) 낮을수록 우선. 적용대상 매칭 후보가 여럿이면 최솟값 1건 선택 |
| `tgt_cond` | JSONB | NN | `'[]'` | (제거됨 — 개정 노트 참조) 적용대상 조건 (§8.3 조건 배열). **빈 배열 = 전체 매칭** |
| `unt_splt_yn` | BOOLEAN | NN | false | 입수 단위 배수 절사. 입수 = ea_qty(입고단위) ÷ ea_qty(출고단위). true면 로케이션별 배정수량을 입수 배수로 내림 — 낱개 혼적 방지. 몫 0인 로케이션은 자동 스킵 |
| `loc_srt` | JSONB | NN | `'[]'` | 후보 정렬 기준 목록 (§8.4). 빈 배열이면 기본 정렬(피킹순위 ASC → 로케이션코드 ASC) |
| `last_rvsn_no` | BIGINT | NN | 1 | 마지막 저장 리비전 |
| 감사 4종 | | | | |

제약:

```sql
CONSTRAINT ck_ptawy_stgy_prty CHECK (prty >= 0)
CONSTRAINT ck_ptawy_stgy_tgt_cond CHECK (jsonb_typeof(tgt_cond) = 'array')
CONSTRAINT ck_ptawy_stgy_loc_srt  CHECK (jsonb_typeof(loc_srt) = 'array')
```

- (prty) 유니크는 걸지 않는다 — 동률은 허용하고 선택 시 `prty, ptawy_stgy_id` 순으로 결정적이게 한다. 동률 경고는 화면·저장 서비스가 담당.
- 재설계안의 분할정책 중 `defaultMaxLoadQty`·`countPendingMoves`·`skipWhenBelowOneCase`는 두지 않는다 — 근거는 `전략_테이블설계안.md` §3.4 (현행 스키마 불변식이 이미 해결했거나 잉여).

```sql
CONSTRAINT ck_ptawy_stg_line_cond CHECK (jsonb_typeof(line_cond) = 'array')
```

## 8. JSONB 구조 정의 (저장 시 서버 검증 스키마)

### 8.1 `stgy_rvsn.snpsht`

정의 전체를 API 응답 DTO와 같은 형태로 직렬화한다. 예 (적치):

```json
{
  "stgyNm": "상온 기본", "prty": 10, "untSpltYn": true,
  "tgtCond": [{"fld": "TMP_ZON", "op": "EQ", "vals": ["DRY"]}],
  "locSrt": [{"field": "PIKNG_PRTY", "dir": "ASC"}],
  "stages": [
    {"srtSeq": 1, "mthdCd": "SAME_PROD_LOC", "mthdPara": {}, "lineCond": [], "locCond": [{"fld": "ZON", "op": "IN", "vals": ["DRY-A"]}]}
  ]
}
```

### 8.2 `stgy_exec_log.dcsn_trc`

검수 (`INSP`) — 라인 × 규칙:

```json
[{"ibLineId": 7, "prodCd": "PROD-0001",
  "rules": [
    {"ruleCd": "SHELF_LIFE_PCT", "pass": false, "actual": "27%", "expected": ">= 30%", "msg": "잔여 27% < 최소 30% (입고가능 마지막 일자 2026-07-28)"},
    {"ruleCd": "LOT_DATE_REVERSE", "pass": true},
    {"ruleCd": "SHELF_LIFE_PCT", "skip": "유통기한 미관리 상품"}]}]
```

적치 (`PTAWY`) — 단계 × 후보:

```json
{"reqQty": 40, "asgnQty": 40,
 "stages": [
   {"srtSeq": 1, "mthdCd": "SAME_PROD_LOC", "gate": "PASS",
    "locs": [{"locCd": "DRY-A-01-01", "avalQty": 24, "asgnQty": 24},
             {"locCd": "DRY-A-01-02", "avalQty": 0, "asgnQty": 0, "skip": "적재 가능 수량 없음"}]},
   {"srtSeq": 2, "mthdCd": "EMPTY_LOC", "gate": "PASS",
    "locs": [{"locCd": "DRY-B-02-01", "avalQty": 48, "asgnQty": 16}]}]}
```

웨이브 (`WAV`) — 주문 × 조건그룹. 편입/미편입 주문을 **모두** 담는다 (제외된 주문과 사유가 남아야 한다):

```json
{"tgtCount": 12, "matchedCount": 9,
 "orders": [
   {"outbOrderId": 31, "outbNo": "OB-20260803-001", "outbTyp": "NRML", "vhclFltno": "1",
    "storeCd": "ST-0001", "storeNm": "강남점", "odrDe": "2026-08-03", "matched": true,
    "grps": [{"idx": 0, "pass": true,
              "conds": [{"fld": "OUTB_TYP", "op": "EQ", "expected": ["NRML"], "actual": "NRML", "pass": true},
                        {"fld": "VHCL_FLTNO", "op": "EQ", "expected": ["1"], "actual": "1", "pass": true}]},
             {"idx": 1, "pass": false,
              "conds": [{"fld": "OUTB_TYP", "op": "EQ", "expected": ["RTNGS"], "actual": "NRML", "pass": false}]}]}]}
```

- 첫 통과 그룹에서 멈추지 않고 **전 그룹을 평가**한다 — 편입 여부는 같지만 "2번 그룹은 왜 안 걸렸나"를 화면이 보여줄 수 있어야 하기 때문.
- 편입 0건이라 웨이브를 만들지 않은 실행도 같은 구조로 남는다 (`tgt_ref`만 NULL).

### 8.3 조건 배열 (`tgt_cond` · `line_cond` · `loc_cond` · `cond_grp` 공통)

```json
[{"fld": "TMP_ZON", "op": "EQ", "vals": ["DRY"]}]
```

- `fld`: 필드 레지스트리 enum code. 등록 필드 —
  - `putaway-target` (적용대상·라인 조건 공용): `TMP_ZON` 상품 온도대 · `VNDR` 입고 벤더(vndr_cd) · `PROD` 상품(prod_cd) · `INB_UOM` 입고단위(prod.inb_uom_cd — "파렛트 입고는 보관존으로" 류의 단계 분기용)
  - `putaway-loc` (로케이션 조건): `ZON` 존(zon_cd) · `LOC_CD` 로케이션코드(LIKE 허용) · `BIZ_DVSN` 존 업무유형(zon.biz_dvsn — 보관/피킹 등 로케이션 성격 구분, 후보 조회가 존을 조인해 판정)
- `op`: `EQ | NE | IN | NOT_IN | GE | LE | BETWEEN | LIKE`. 필드마다 허용 연산자가 레지스트리에 선언되고 저장 시 검증된다.
- `vals`: 항상 문자열 배열. 개수 검증 — EQ/NE/LIKE=1, BETWEEN=2, IN/NOT_IN=1..n.
- 배열 원소 간은 AND. 웨이브의 `cond_grp`만 **배열의 배열**이고, 바깥 원소(그룹) 간이 OR다 (§10.1).
  - `wave-order` (웨이브 편성 조건): `OUTB_TYP` 출고유형(outb_order.outb_typ, 공통코드 OUTB_TYP) · `VHCL_FLTNO` 차량편수(outb_order.vhcl_fltno, 공통코드 VHCL_FLTNO). 둘 다 코드값이라 등가 연산자(EQ/NE/IN/NOT_IN)만 허용한다 — 사전순 대소 비교는 `"10" < "2"`가 되어 의미가 없다. 납품처그룹·납품처유형은 `store`에 대응 컬럼이 없어 **보류**

### 8.4 `loc_srt` 정렬 기준 배열

```json
[{"field": "PIKNG_PRTY", "dir": "ASC"}, {"field": "LOC_CD", "dir": "ASC"}]
```

- `field`: `PIKNG_PRTY`(loc.pikng_prty) | `PTAWY_PRTY`(loc.ptawy_prty — 적치 우선순위) | `LOC_CD`. `dir`: `ASC` | `DESC`. 앞 기준부터 적용.

### 8.5 `para` (규칙·방식 파라미터)

키·타입·범위는 각 구성요소 Descriptor의 ParamSpec이 정의하고, 저장 시 그 스키마로 검증한다. DB는 "검증을 통과한 JSON"만 담는다 — 테이블 설계서에는 개별 키를 고정하지 않는다 (구현체 추가·변경 시 문서가 아니라 Descriptor가 진실).

## 10. wav_stgy — 웨이브 전략 (2차, 2026-08-03)

웨이브 도메인은 **테이블 1개로 끝난다.** 조건그룹에는 개별 파라미터도 활성 플래그도 없고 항상 헤더와 통째로 저장·검증되므로, §1.2(편집 단위 = 저장 단위) 기준에서 행이 아니라 JSONB다.

| 컬럼 | 타입 | NULL | 기본값 | 설명 |
|---|---|---|---|---|
| `wav_stgy_id` | BIGINT IDENTITY | NN | | PK |
| `stgy_nm` | VARCHAR(100) | NN | | 전략명 (표시용 — 실행에 사용하지 않는다) |
| `prty` | INTEGER | NN | 0 | 실행 순서. 낮을수록 먼저. 동률은 `wav_stgy_id` 순으로 결정적이게 |
| `cond_grp` | JSONB | NN | | 조건그룹 `[[{fld,op,vals},…],…]` — 그룹끼리 OR, 그룹 안 AND (§8.3). 필드는 `OUTB_TYP`·`VHCL_FLTNO` |
| `last_rvsn_no` | BIGINT | NN | 1 | 마지막 저장 리비전 |
| 감사 4종 | | | | |

제약:

```sql
CONSTRAINT ck_wav_stgy_prty CHECK (prty >= 0)
CONSTRAINT ck_wav_stgy_cond_grp CHECK (
    jsonb_typeof(cond_grp) = 'array' AND jsonb_array_length(cond_grp) > 0
)
```

### 10.1 적치와 달리 `prty`를 두는 이유

적치는 「적용대상(발주구분) 일치 전략 1건 선택」이라 UNIQUE가 우선순위를 대체했다. 웨이브는 **전 전략을 순회하며 각각 웨이브를 만드는** 유형이라 실행 순서가 결과를 바꾼다 — 한 주문은 웨이브 하나에만 속하므로 **먼저 실행된 전략이 선점**한다. 적치를 따라 `prty`를 지우면 편성 결과가 비결정적이 된다.

### 10.2 조건 0건 방어가 두 겹인 이유

`ck_wav_stgy_cond_grp`는 배열 길이만 본다. `[[]]`(빈 그룹 1개)는 CHECK를 통과하지만, 조건 0건 그룹은 「무조건 참」이라 미편성 주문 전부를 한 웨이브에 쓸어담는다. **빈 그룹 거부는 저장 서비스(`WavStgyService.validate`)가 하는 유일한 방어선**이다 — 자식 행 개수를 CHECK로 볼 수 없는 적치의 「단계 0건」과 같은 성격의 한계다.

### 10.3 기존 테이블 변경

```sql
-- outb_wave: 이 웨이브를 만든 전략·리비전. 둘 다 NULL = 화면에서 수동 생성
ALTER TABLE outb_wave ADD COLUMN wav_stgy_id BIGINT, ADD COLUMN rvsn_no BIGINT;
ALTER TABLE outb_wave ADD CONSTRAINT ck_outb_wave_stgy
    CHECK ((wav_stgy_id IS NULL) = (rvsn_no IS NULL));

-- outb_order: 편성 조건의 기준값. 기존 행은 DEFAULT로 일반출고가 되고 배차는 미정(NULL)
ALTER TABLE outb_order ADD COLUMN outb_typ VARCHAR(10) DEFAULT 'NRML' NOT NULL;
ALTER TABLE outb_order ADD COLUMN vhcl_fltno VARCHAR(10);

-- outb_order: 편입 출처. NULL = 미편성. 기존 편성분은 마이그레이션에서 MANUAL로 채운다
ALTER TABLE outb_order ADD COLUMN wav_reg_typ VARCHAR(10);
ALTER TABLE outb_order ADD CONSTRAINT ck_outb_order_wav_reg CHECK (
    (wav_id IS NULL AND wav_reg_typ IS NULL)
    OR (wav_id IS NOT NULL AND wav_reg_typ IN ('STGY','MANUAL'))
);
```

- 전략 컬럼은 **전략이 실제로 실행해 만든 행에만 채운다** — 수동 처리한 행에까지 전략 id를 채우면 "전략 id 있음 ≠ 전략 실행됨"이 되어 추적이 무의미해진다. 짝 CHECK가 그 규약을 DB로 굳힌다.
- `wav_reg_typ`은 `wav_id`와 짝이다. **편성 해제·주문 취소 경로가 둘을 함께 비워야** 제약을 어기지 않는다 (`OutbOrder.unassignWave()`가 두 필드를 같이 지우고, `cancel()`이 그것을 호출한다).
- `wav_reg_typ`의 근거: 조건으로 표현하기 어려운 묶음은 결국 수동으로 편성하게 된다. 금지 대상이 아니라 **가시화** 대상이다 — 전략 조건과 맞지 않는 주문이 웨이브에 있는 상황을 화면이 구분해 보여준다.
- 웨이브 전략을 삭제해도 `outb_wave.wav_stgy_id`는 남는다 — 느슨한 참조라 "무엇이 만들었는지"의 기록으로 유효하다.
- `outb_typ`·`vhcl_fltno`에 CHECK를 걸지 않는 이유는 `ptawy_stgy.odr_dvsn`과 같다 — **값 목록의 주인은 공통코드(코드관리 화면)**이고, 존재 검증은 주문 등록 서비스가 한다. 편수가 늘어도 DDL 변경이 없다.
- 공통코드 2그룹을 함께 신설한다: `OUTB_TYP`(NRML 일반출고 / RTNGS 반품출고) · `VHCL_FLTNO`(1·2·3편). `NRML`은 `outb_typ`의 컬럼 DEFAULT가 가리키는 값이라 지우면 안 된다.
