## 1. 개요와 액터

| 액터 | 역할 |
|---|---|
| **관리자** | 전략 정의를 등록·수정·삭제하고, 미리보기로 검증한 뒤 운영에 반영한다 |
| **작업자** | 검수 화면에서 검수 저장, 적치 화면에서 적치 실행을 한다. 전략은 작업자에게 "차단 메시지"(검수)와 "추천 결과"(적치)로 나타난다 |
| **시스템** | 업무 서비스(검수 저장·적치 추천)가 전략 서비스를 호출해 판정/산정하고, 실행 로그(`stgy_exec_log`)와 리비전(`stgy_rvsn`)을 기록한다 |

설계 불변 원칙 (전 프로세스 공통):

- **P1** 화면에 보이는 옵션 = 코드에 구현된 실행기. 옵션 목록은 코드 레지스트리(Descriptor)에서만 나온다.
- **P2** 관리자가 저장하는 것은 "정의"이고, 저장 시 서버가 파라미터 스키마(ParamSpec)·조건 필드 레지스트리로 검증한다. 검증 실패 = 저장 거부. "등록은 되는데 실행하면 오류"인 상태를 만들지 않는다.
- **P4** 모든 전략은 저장 전에 같은 로직으로 미리보기(Dry-run)할 수 있다.
- **P5** 전략 저장마다 리비전 스냅샷을 남기고, 실행 기록에는 리비전 번호와 판정 근거를 남긴다.
- **D4** 사용여부 컬럼 없음 — 실행 제외 = 물리삭제. 리비전 스냅샷은 조회 전용 감사 이력으로 남는다 (2026-08-02 개정: 복원 흐름 제거 — §4.3).

## 2. PR-01 검수 제약 실행 프로세스

### 2.1 요약

검수 저장 직전에 정책의 규칙 전부를 라인별로 AND 평가하고, **위반이 하나라도 있으면 검수 저장 전체를 거부**한다. 위반은 첫 건에서 중단하지 않고 **전부 수집해 한 번에** 반환한다.

### 2.2 트리거와 통합 지점

- 트리거: 작업자의 검수 저장 — `POST /inbound/asns/{ibOrderId}/receive` (기존 엔드포인트, 변경 없음)
- 통합 지점: `ReceivingService.receive()` 안, 라인 순회(`receiveLine`) **시작 전**. 정책 평가 → 통과 시에만 기존 저장 로직 진행. 기존의 "요청 라인 중 한 건이라도 실패하면 전체 롤백" 트랜잭션 단위를 그대로 계승한다.

### 2.3 흐름

```
[작업자] 검수 저장 요청 (라인별 검수수량·제조일자·입고일자)
    │
[시스템] 1. 검수 정책 조회 (insp_plcy — 전역 1행)
    │       └ 정책 없음 또는 규칙 0건 → 제약 없이 기존 검수 저장 진행 (검수 자체를 막지 않는다)
    │
    ├──── 2. 요청 라인별로 규칙 전부 평가 (InspectionContext: 상품, 입고일자, 제조일자, 기존 재고 로트 조회 포트)
    │       ├ 관리 대상 아님 스킵: 유통기한 미관리 상품(prod.shelf_life_days IS NULL)이거나
    │       │  규칙이 보는 로트 속성이 없는 라인 → 그 규칙은 통과로 간주 (단, trace에 스킵 사유가 남는다)
    │       └ 위반 발생해도 중단하지 않고 계속 — 라인×규칙 전체의 위반 목록을 수집
    │
    ├──── 3-a. 위반 0건 → 기존 검수 저장 로직 실행 (라인 수량 누계 + Lot + 스테이징 재고 + 이력)
    │            └ stgy_exec_log 기록: trgr_typ=MANUAL, tgt_ref=입고번호, 결과 "라인 N건 전부 통과"
    │
    └──── 3-b. 위반 ≥1건 → 예외로 전체 거부 (HTTP 400/409, 위반 목록 포함 — 라인·규칙·실제값·기대값)
                 └ stgy_exec_log 기록: 같은 구조, 결과 "라인 N건 중 위반 M건" + dcsn_trc(건별 판정)
```

### 2.4 규칙 카탈로그 (1차 구현 — 레지스트리 등재분만 화면에 노출)

| rule_cd | 이름 | 파라미터 | 판정 (위반 조건) |
|---|---|---|---|
| `LOT_DATE_REVERSE` | 역순제한 | `excludeSameDay: BOOLEAN` (기본 true) | 입력 제조일자 < 해당 상품 **보유 재고(on_hand>0) 로트의 최대 제조일자**. excludeSameDay=true면 입고일자가 당일인 로트는 최댓값 계산에서 제외 — 암묵 동작으로 두지 않고 파라미터로 노출한다 |
| `SHELF_LIFE_PCT` | 유통기한 잔여비율 | `minPercent: NUMBER (0~100)` | 잔여% = (제조일자 + 유통기한일수 − 입고일자) ÷ 유통기한일수 × 100 이 minPercent **미만**. 위반 메시지에 잔여%·입고 가능 마지막 일자를 포함한다. 제조일자 기준과 유통기한 기준은 같은 값을 다른 쪽에서 재는 것이라 규칙을 하나만 둔다 |

### 2.5 예외·경계

- 정책 평가 자체의 오류(저장 정의가 배포본 레지스트리에 없는 rule_cd 등)는 검수를 통과시키지 않고 **오류로 중단**한다. 단 이 상태는 P2 저장 검증 때문에 정상적으론 발생할 수 없고, 발생 시 운영 알람 대상이다.
- 검수 취소(`cancelReceipt`)는 제약 평가 대상이 아니다 — 제약은 "들어오는 것"만 본다.
- 미리보기(`PREVIEW`)는 같은 평가 함수를 쓰되 DB 변경 없이 판정 결과만 반환한다 (§4.4).

## 3. PR-02 적치 전략 실행 프로세스

### 3.1 요약

적치 화면에서 (입고 라인, Lot) 배치를 고르면, 시스템이 전략을 선택해 **단계(Step) 순서대로 후보 로케이션을 찾고 (로케이션, 수량) N행의 추천**을 만든다. 작업자는 추천을 그대로 실행하거나 수정할 수 있다 — **전략은 추천이고, 실행은 현행 즉시 MOVE 흐름을 유지**한다.

> 현행과의 관계: 지금 적치는 지시(putaway_task) 없이 수동 선택 → 즉시 MOVE다(`PutawayService.putaway()`).
> 1차에서는 이 실행 흐름을 바꾸지 않고 **후보 선택 단계만 전략이 대체**한다. `putaway_task` 기반
> 지시 생성/실행 분리는 스키마·설계문서에 준비돼 있으나 현행 코드가 쓰지 않으므로 (docs/design.md와
> 코드의 기존 어긋남), 이번 범위에서 손대지 않는다.

### 3.2 트리거와 통합 지점

- 트리거: 적치 화면에서 배치 선택 시 추천 요청 — **신규** `POST /inbound/putaway/lines/{ibLineId}/recommend` (body: `lotId`, `qty`)
- 실행: 기존 `POST /inbound/putaway/lines/{ibLineId}` 그대로 (추천 결과의 로케이션·수량별로 호출). 온도대 일치·STORAGE 검증 등 기존 가드는 실행 측에 그대로 남는다.
- 기존 수동 후보 조회(`GET .../candidate-locs`)는 유지한다 — 전략 미설정이거나 추천을 무시하고 싶을 때의 경로.

### 3.3 흐름

```
[작업자] 배치 선택 (입고 라인, Lot, 적치할 수량)
    │
[시스템] 1. 전략 선택 (2026-08-03 개정): ib_order.odr_dvsn과 일치하는 전략 → 없으면 전체(odr_dvsn NULL) 전략
    │       유형당 1개(UNIQUE)라 우선순위 없이 결정적. (원안의 tgt_cond 매칭 + prty 선택은 폐기 —
    │       적용대상은 발주구분 단일 선택으로 좁히고, 라인 분기는 단계 조건이 전담)
    │       └ 매칭 전략 없음 → "적치 전략 미설정" 응답. 화면은 기존 수동 후보 목록으로 폴백
    │
    ├──── 2. 잔여수량 ← 요청수량. 단계(ptawy_stgy_stg)를 srt_seq 순으로:
    │       a. line_cond(조건 — 이 조건일 때만 이 단계 적용) 불일치 → 다음 단계 (trace에 "조건 불일치" 기록)
    │       b. 방식(mthd_cd)으로 후보 조회 → loc_cond(적치위치 지정 — 존 업무유형 IN 최대 1건)로 필터 → loc_srt로 정렬
    │          ※ 상품 온도대 일치 + STORAGE는 조건이 아니라 모든 방식의 불변 전제 (현행 putaway() 가드와 동일)
    │       c. 후보마다: 적재가능 = max(0, loc.max_qty − 현재고(그 로케이션 전체 상품))
    │          - unt_splt_yn=true면 입수 단위 배수로 절사 (입수 = ea_qty(입고단위)/ea_qty(출고단위))
    │          - 배정수량 > 0 → 배정, 잔여 차감. 잔여 0 → 종료
    │
    ├──── 3. 결과: (로케이션, 수량) N행 + 단계별 trace (게이트 통과/탈락, 후보별 배정)
    │       └ 잔여 > 0 → 부분 추천으로 반환 (배정분 + 미배정 잔여 표시). 실행 여부는 작업자 판단
    │
    ├──── 4. stgy_exec_log 기록: trgr_typ=MANUAL, tgt_ref=입고번호, rvsn_no, dcsn_trc(단계별)
    │
[작업자] 5. 추천 확인/수정 → 행별로 기존 적치 실행 API 호출 (즉시 MOVE, 기존 가드 그대로)
```

### 3.4 방식(추천 방식) 카탈로그 (1차)

| mthd_cd | 이름 | 후보 판정 |
|---|---|---|
| `SAME_PROD_LOC` | 적재로케이션 | 같은 상품 재고(on_hand>0)가 이미 있는 보관 로케이션 |
| `EMPTY_LOC` | 빈로케이션 | 재고 0(행 없음 포함)인 보관 로케이션 |
| `ANY_LOC` | 전체 보관 | 온도대 일치 보관 로케이션 전부 — 현행 수동 후보 목록과 동일한 모집단. 마지막 단계의 안전망 용도 |

`FIXED_LOC`(고정로케이션)은 **1차 제외** — 현행 마스터에 고정상품(로케이션-상품 고정) 개념이 없다. 도입하려면 `loc`에 고정상품 컬럼(또는 별도 매핑 테이블) 신설이 선행돼야 하며, 그때 방식 구현체 추가만으로 화면에 자동 노출된다.

### 3.5 예외·경계

- 반품입고 분기(반품존으로 별도 적치)는 현행에 재고상태·반품존 개념이 없으므로 범위 외.
  재도입 시 적용대상 선택지에 반품입고(RTNGS)를 추가하면 된다 — ODR_DVSN 공통코드·UNIQUE 체계가 이미 수용한다 (저장 검증·옵션 소스의 필터만 풀면 됨).
- 추천과 실행 사이에 다른 작업자가 먼저 적치해 스테이징 잔량·로케이션 용량이 달라질 수 있다 — 실행 측 기존 가드(잔량 초과 검증, ck_inv_qty)가 최종 방어선이고, 추천은 실행을 예약하지 않는다.
- `loc.max_qty`는 STORAGE에 NOT NULL이 스키마로 강제돼 있어(ck_loc_storage_capacity) "용량 미설정 = 무제한"인 로케이션이 생기지 않는다.

## 4. PR-03 전략 관리 프로세스 (관리자)

### 4.1 등록·수정

```
[관리자] 화면에서 정의 편집 (규칙/단계 추가·삭제·순서변경, 파라미터·조건 입력)
    │      └ 폼의 선택지·입력 스키마는 전부 메타 API(레지스트리 파생)로 렌더링 — P1
    ├─ (선택) 미리보기 — 미저장 정의를 그대로 서버로 보내 Dry-run (§4.4)
    │
[시스템] 저장 요청 검증 — 실패 시 저장 거부(필드 단위 오류 반환):
    │      · rule_cd/mthd_cd가 enum에 존재하고 deprecated 아님
    │      · 파라미터가 규칙별 검증(validatePara — 타입·필수·범위) 충족
    │      · 조건의 필드가 필드 enum에 존재, 허용 연산자, 연산자별 값 개수
    │      · 검수: 같은 rule_cd 중복 금지, 정책은 전역 1행(생성 시 기존 행 있으면 거부 — D8)
    │      · 적치: 적용대상은 전체/정상/긴급만(유형당 1개 — 중복 거부), 적치위치는 업무유형 IN 최대 1건
    │
    └─ 저장 = 정의 반영 + last_rvsn_no 증가 + stgy_rvsn 스냅샷 1행 (한 트랜잭션)
```

### 4.2 삭제 (D4: 실행 제외 = 물리삭제)

- 규칙/단계 삭제: 수정 저장의 일부다 (목록에서 빼고 저장 → 리비전 증가).
- 전략/정책 자체 삭제: 행 삭제 전 **마지막 상태를 리비전으로 이미 보유**하므로 정보 손실이 없다. 삭제 후에도 `stgy_rvsn`·`stgy_exec_log`는 남는다 (느슨한 참조 — stgy_id는 남고 원본만 없음).
- 화면은 삭제 전 확인 다이얼로그에서 "이 전략이 최근 N일간 실행 M회"를 보여줘 오삭제를 줄인다 (실행 로그 집계).

### 4.3 복원 — 제거됨 (2026-08-02 개정)

> 원안의 복원(리비전 스냅샷 재저장·삭제된 전략 재생)은 구현 후 **제거했다.** 리비전은 조회 전용
> 감사 이력이다 — 예전 정의로 되돌리려면 스냅샷 JSON을 보고 편집 화면에서 다시 저장한다.
> 근거: 사용 빈도 대비 코드·화면 복잡도(삭제전략 목록, anchor id 추적, 은퇴 구성요소 재검증 분기)가
> 크다고 판단. 운영에서 복원 요구가 실제로 반복되면 이 절의 원안(스냅샷 재저장 방식)으로 되살린다.

### 4.4 미리보기 (P4)

| 대상 | 입력 | 출력 |
|---|---|---|
| 검수 정책 | 미저장 정의(또는 저장본) + 검수 대기 입고의 라인들 또는 가상 로트(상품·제조일자·입고일자) | 라인×규칙별 통과/위반 + 근거(실제값·기대값). DB 변경 없음 |

- 편집 화면의 우측 패널이 실시간으로 이 API를 호출한다 (좌: 정의 편집 / 우: 미리보기 — 화면설계서 참고).
- 미리보기 실행도 `stgy_exec_log`에 trgr_typ=PREVIEW로 남길 수 있으나 1차는 **저장하지 않는다** (용량·소음 관리, 필요 시 후행 도입).

### 4.5 실행 이력 조회

- 관리자 화면에서 전략별 실행 로그 목록 + 건별 dcsn_trc 펼쳐보기 ("이 라인이 왜 차단됐나 / 이 배치가 왜 이 로케이션에 배정됐나"를 조건 단위로 표시).
- 검수는 산출물이 결과 행이 아니라 "차단"이라 실행 흔적이 남지 않는 유형이다 — 이 로그가 유일한 흔적이다.

## 7. PR-04 웨이브 전략 실행 프로세스 (2차)

### 7.1 요약

미편성 출고 주문을 조건으로 걸러 **웨이브로 묶는다.** 전략 하나가 웨이브 하나를 만들고, 조건에 맞는 주문이 그 웨이브에 편입된다. 조건은 **그룹끼리 OR, 그룹 안 AND**다.

편성의 실체는 `outb_order.wav_id`를 채우는 것이고, 함께 `wav_reg_typ='STGY'`를 남겨 **수동 편성과 구분**한다.

### 7.2 트리거와 통합 지점

- 트리거: **신규** `POST /outbound/waves/stgy-exec` (body: `wavStgyId?`, `odrDeFrom?`, `odrDeTo?` — 날짜는 조건이 아니라 대상 범위)
  - `wavStgyId` 있음 = 선택실행(그 전략만) · 없음 = 전 전략을 우선순위 순으로 실행
- 기존 수동 편성 경로(`POST /outbound/waves`, `POST /outbound/waves/{wavId}/orders`)는 그대로 둔다 — 전략 미설정이거나 조건으로 표현할 수 없는 묶음을 만들 때의 경로다. 수동 편성분은 `wav_reg_typ='MANUAL'`로 남아 화면이 구분 표시한다.
- 실행 전체가 **한 트랜잭션**이다. 도중 실패하면 이번 실행의 편성이 통째로 롤백된다(부분 편성 없음).

### 7.3 흐름

```
[관리자] 전략 실행 요청 (전체 / 특정 전략, 선택적으로 주문일 범위)
    │
[시스템] 1. 실행할 전략 선별 — 지정이 없으면 전 전략을 prty ASC, id ASC 순으로
    │       └ 전략 0건 → "실행할 웨이브 전략이 없습니다" 오류
    │
    ├──── 2. 편성 대상 주문 조회 (한 번만) — 상태 CREATED(신규) AND 웨이브 미편성
    │       · 주문일 범위가 있으면 그 범위로 좁힌다 (조건이 아니라 실행 스코프)
    │       · 취소·할당 이후 주문은 상태 조건에서 자연히 빠진다
    │
    ├──── 3. 전략마다 순서대로:
    │       a. 남은 후보 주문마다 조건 판정 (그룹 OR / 조건 AND) — 판정과 동시에 조건 단위 근거 수집
    │       b. 편입 0건 → 웨이브를 만들지 않고 다음 전략으로 (사유를 결과에 담는다)
    │       c. 편입 ≥1건 → 웨이브번호 채번 → outb_wave 생성(wav_stgy_id·rvsn_no 기록, 상태 PLANNED)
    │                     → 주문에 wav_id + wav_reg_typ=STGY 기록
    │       d. 편입된 주문을 후보 목록에서 제거 → 뒤 전략은 남은 주문만 본다 (선점)
    │       e. stgy_exec_log 기록: trgr_typ=MANUAL, tgt_ref=웨이브번호, dcsn_trc(주문별 판정)
    │
    └──── 4. 결과: 전략별 {웨이브번호, 편입 건수} + 전체 대상/편입 건수
```

### 7.4 조건 필드 카탈로그 (2차 구현)

| fld | 이름 | 허용 연산자 | 값 |
|---|---|---|---|
| `OUTB_TYP` | 출고유형 | EQ · NE · IN · NOT_IN | 공통코드 `OUTB_TYP` — NRML 일반출고 / RTNGS 반품출고 (선택지: `outbTyps`) |
| `VHCL_FLTNO` | 차량편수 | EQ · NE · IN · NOT_IN | 공통코드 `VHCL_FLTNO` — 1편·2편… (선택지: `vhclFltnos`) |

두 값은 `outb_order`에 신설한 컬럼(`outb_typ`·`vhcl_fltno`)이다. 웨이브가 「같은 유형·같은 차수에 실릴 주문만 묶는」 단위이므로, 편성 조건의 기준값이 주문 헤더에 있어야 한다.

**보류 — 납품처그룹 · 납품처유형:** 점포 마스터(`store`)에 그룹·유형 컬럼이 없어 값을 꺼낼 곳이 없다. 「등록만 되고 동작하지 않는 옵션」을 만들지 않는다는 P1 때문에 컬럼 신설이 선행돼야 하며, 그때 `WaveOrderField`에 상수 두 개를 추가하면 화면·저장 검증·실행에 동시에 반영된다.

- **대소·범위 연산자를 열지 않는다.** 조건 비교가 문자열 사전순이라 차량편수에 GE/LE를 열면 `"10"`이 `"2"`보다 앞선다 — 코드값 필드에는 등가 비교만 의미가 있다. 같은 이유로 수량류 숫자 필드도 두지 않는다(필요해지면 연산자 계층에 타입을 먼저 넣어야 한다).
- **배차 미정(`vhcl_fltno` NULL)** 주문은 등가 조건에 걸리지 않고 부정 연산자(NE·NOT_IN)에만 참이 된다 — `ConditionOperator`의 null 규약 그대로다.
- 라인에서 파생하는 값(상품·온도대)은 조건으로 두지 않는다. **편성 단위가 주문**이라, 온도대가 섞인 주문을 "냉장 웨이브"로 보내면 상온 라인까지 함께 끌려가 전략 이름과 실제 동작이 어긋난다.
- 필드 추가 = `WaveOrderField` enum 상수 추가.

### 7.5 재실행 안전 — 빈 웨이브를 만들지 않는다

**편입 0건이면 웨이브를 만들지 않는다.** 이것이 재실행 방지 장치를 대신한다:

1. 첫 실행에서 조건에 맞는 주문이 편성된다 → 그 주문들은 `wav_id`가 차서 대상 조회에서 빠진다
2. 두 번째 실행은 같은 조건으로 0건 매칭 → 웨이브를 만들지 않고 끝난다

별도의 "오늘 이미 실행됨" 키가 필요 없고, 실행 후 새 주문이 들어오면 다시 실행해 편성할 수 있다(하루 1회 제한이 없다). 빈 웨이브는 어차피 별도로 치워야 하는 찌꺼기이므로 애초에 만들지 않는 편이 낫다.

### 7.6 우선순위 = 선점 순서

한 주문은 웨이브 하나에만 속한다(`OutbOrder.assignWave`가 중복 편성을 거부). 따라서 여러 전략의 조건에 동시에 맞는 주문은 **먼저 실행된 전략이 가져간다.** `prty`가 낮을수록 먼저이고, 동률이면 `wav_stgy_id` 순이라 결과가 항상 결정적이다.

관리자가 이 순서를 화면에서 그대로 읽을 수 있도록 목록도 같은 순서로 정렬한다.

### 7.7 예외·경계

- **조건 0건 전략은 저장 자체를 거부**한다 (그룹 0건은 DB CHECK, 빈 그룹은 저장 서비스). 조건이 없으면 미편성 주문 전부가 한 웨이브에 들어간다.
- 편성 대상은 **신규(CREATED) + 미편성**뿐이다. 주문 헤더에는 보류·마감 개념이 없으므로 별도 제외 조건이 없다(보류는 재고 쪽 `inv.hld_qty`의 개념이다).
- 실행과 실행 사이에 다른 사용자가 같은 주문을 수동 편성할 수 있다 — `assignWave`의 중복 편성 거부가 최종 방어선이고, 이 경우 실행 트랜잭션이 롤백된다.
- 웨이브 전략을 삭제해도 이미 만들어진 웨이브와 편성은 그대로 남는다. `outb_wave.wav_stgy_id`는 느슨한 참조라 "무엇이 만들었는지"의 기록으로 유효하다.
- 미리보기는 같은 판정 함수를 쓰되 아무것도 쓰지 않는다 — 실행 로그도 남기지 않는다(§4.4와 동일).

### 7.8 미리보기

`POST /strategy/wave-strategies/preview` (미저장 정의) · `/{id}/preview` (저장본). 입력은 정의 + 주문일 범위, 출력은 **대상 주문 전체**의 `{주문, 편입 여부, 그룹별·조건별 판정}`이다.

편입되는 주문만이 아니라 **제외되는 주문과 그 사유까지** 돌려주는 것이 핵심이다 — 실행 화면은 "몇 건이 왜 빠졌는지" 알려주지 않으므로, 저장 전에 그것을 확인할 수 있어야 이름과 조건이 어긋난 전략이 운영에 나가지 않는다.
