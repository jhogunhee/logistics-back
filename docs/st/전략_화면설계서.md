```
┌───────────────────────────────────────────────────────────────┐

├──────────────────────────────┬────────────────────────────────┤
```

## 3. SC-01 검수 정책관리

### 3.1 목적·특성

검수 확정 시 전 라인에 AND로 실행되는 규칙 목록을 관리한다. 정책은 **전역 1개** — 목록 화면이 없고 진입하면 바로 편집 화면이다. 정책 미존재 시 빈 상태 화면("검수 제약이 없습니다. 정책 만들기")을 보여준다.

**전략 선택·우선순위 개념이 없음을 화면이 그대로 드러낸다** — 우선순위 입력칸이 없고, 헤더에 "등록된 규칙은 모든 검수 저장에서 전부 실행됩니다" 고정 안내를 둔다 ("여러 개 만들면 하나가 골라진다"는 오해를 막는다).

### 3.2 레이아웃

```
┌───────────────────────────────────────────────────────────────────────┐
│ 검수 정책관리            정책명 [________]   [리비전 이력][삭제][저장] │
│ ⓘ 등록된 규칙은 모든 검수 저장에서 전부(AND) 실행됩니다.               │
├────────────────────────────────────┬──────────────────────────────────┤
│ 규칙 목록                [+ 규칙]  │ 미리보기                         │
│ ┌────────────────────────────────┐ │ 대상: (◉ 검수 대기 입고 선택 ▾)  │
│ │ ≡ 유통기한 잔여비율     [삭제] │ │       (○ 가상 로트 직접 입력)    │
│ │   최소 잔여비율(%) [ 30 ]      │ │       [미리보기 실행]            │
│ ├────────────────────────────────┤ │ ┌──────────────────────────────┐ │
│ │ ≡ 역순제한             [삭제] │ │ │ 라인   규칙        판정  사유 │ │
│ │   당일 입고분 제외 [✓]         │ │ │ PROD-1 잔여비율   ✕ 27%<30%  │ │
│ └────────────────────────────────┘ │ │ PROD-1 역순제한   ○           │ │
│  (규칙 0건이면: "제약 없음 —       │ │ PROD-2 (미관리 상품 — 스킵)   │ │
│   모든 검수가 통과합니다")         │ └──────────────────────────────┘ │
└────────────────────────────────────┴──────────────────────────────────┘
```

### 3.3 구성 요소

| 항목 | 컴포넌트 | 동작·검증 |
|---|---|---|
| 정책명 | 텍스트 (필수, 100자) | 표시용 — "실행에 사용되지 않음" 툴팁 |
| [+ 규칙] | `ComponentPicker` (`/strategy/meta/inspection-rules`) | 이미 등록된 rule_cd는 목록에서 비활성 (중복 등록 금지 — 서버 검증과 동일 규칙을 화면이 선반영) |
| 규칙 카드 | `DynamicParamForm` (규칙의 ParamSpec) | 카드 제목=규칙 이름, 부제=Descriptor 설명(동작을 문장으로). ≡ 핸들로 순서 변경(srt_seq — 평가 순서이자 위반 목록 표시 순서) |
| 규칙 [삭제] | — | 카드 즉시 제거 (저장 시점에 반영). D4 — 비활성 토글 없음 |
| 미리보기 대상 | 검수 대기 입고 드롭다운(기존 `/inbound/asns?status=…` 재사용) 또는 가상 로트 입력(상품 Picker + 제조일자 + 입고일자) | `POST /strategy/inspection-policy/preview` (미저장 정의 body) |

### 3.4 API 매핑

| 화면 동작 | API |

| 리비전 | `GET …/revisions`, `POST …/revisions/{no}/restore` |

## 4. SC-02 적치 전략관리

> **[2026-08-03 개정]** 아래 원안 중 다음이 구현에서 바뀌었다 (카드1 절충안 — 프로세스정의서 §3.3 개정 참조):
> - **적용대상**: ConditionBuilder(범용 조건) → **발주구분 드롭다운** (전체/정상/긴급 — 유형당 전략 1개).
>   목록의 "적용대상 요약" 컬럼도 발주구분 칩 하나로 대체.
> - **우선순위**: 입력칸·컬럼 제거 — 유형당 1개 UNIQUE가 선택을 결정적으로 만든다
>   (선택 규칙: 유형 일치 → 전체 → 수동 폴백).
> - **단계 카드**: "라인 조건" 라벨 → "조건 — 이 조건일 때만 이 단계 적용"(ConditionBuilder 유지).
>   "로케이션 조건" ConditionBuilder → **적치위치 지정**(존 업무유형 멀티선택, 연산자 없음 — `LocAssignPicker`).
> - **미리보기**: "다른 전략이 우선 매칭" 경고 제거 — 유형 매칭이라 편집 중 전략이 곧 선택될 전략이다.

### 4.1 목적·특성

적치 추천의 단계(어떤 방식으로 어디에 둘지)와 정책(단위 절사·후보 정렬)·적용대상(발주구분)을 관리한다. 전략이 유형별로 **여러 개**(최대 유형 수 + 전체 1개)일 수 있으므로 목록 → 편집 2단 구성이다.

### 4.2 목록 화면

```
┌──────────────────────────────────────────────────────────────┐
│ 적치 전략관리                                    [+ 새 전략] │
│ ┌──────────────────────────────────────────────────────────┐ │
│ │ 우선순위  전략명        적용대상 요약        단계  수정일 │ │
│ │    10     상온 기본     온도대=상온          2     08-02  │ │
│ │    20     전체 폴백     (전체 대상)          1     08-02  │ │
│ └──────────────────────────────────────────────────────────┘ │
│ ⓘ 적치 추천 시 적용대상이 맞는 전략 중 우선순위가 가장       │
│   낮은(앞선) 1개가 선택됩니다.                               │
└──────────────────────────────────────────────────────────────┘
```

- **적용대상 요약 컬럼이 핵심이다** — 전략명과 실제 조건이 어긋난 채 운영되는 것을 화면 차원에서 막는다. 이름이 아니라 조건 요약을 항상 병기한다.
- 행 클릭 → 편집 화면. 목록에서의 인라인 편집은 없다.

### 4.4 구성 요소

| 항목 | 컴포넌트 | 동작·검증 |
|---|---|---|
| 전략명 / 우선순위 | 텍스트 / 숫자(0 이상) | 우선순위 안내: "낮을수록 먼저 선택" |

## 6. SC-03 웨이브 전략관리 (2차, `/strategy/wave`)

SC-02와 같은 골격(목록 → 좌 편집 + 우 미리보기)을 그대로 쓴다. **웨이브는 구성요소(방식·규칙) enum이 없는 유일한 도메인**이라 `ComponentPicker`·`RuleParamForm`을 쓰지 않는다 — 편집기의 본체는 `ConditionBuilder` 뿐이다.

### 6.1 목록

| 열 | 내용 |
|---|---|
| 우선순위 | 낮을수록 먼저 실행. **표 정렬 순서 = 실행 순서 = 선점 순서** |
| 전략명 / 조건그룹 수 / 조건 수 / 수정일시 | |

상단 버튼: `[실행 이력]` · `[전체 실행]` · `[새 전략]`. 전략이 0건이면 안내 문구 — "전략이 없으면 웨이브는 화면에서 수동으로만 편성됩니다."

### 6.2 편집 — 좌: 조건그룹

```
┌ 그룹 1 ─────────────────────── 조건끼리 AND ─┐
│  출고유형     [=]        일반출고              │
│  차량편수     [=]        1편                  │
└──────────────────────────────────────────────┘
             ──────  OR  ──────
┌ 그룹 2 ─────────────────────────────────────┐
│  출고유형     [=]        반품출고              │
└──────────────────────────────────────────────┘
```

- 그룹 사이에 **호박색 "OR" 구분선**을 그려 결합자를 눈으로 읽게 한다. 그룹 헤더에는 "조건끼리 AND".
- 조건 편집은 `ConditionBuilder` 재사용 — 필드·허용 연산자·값 선택지는 전부 메타 API(`fields/wave-order`, `options/outbTyps`·`options/vhclFltnos`)에서 온다. 편수가 코드관리 화면에서 늘면 조건 선택지도 함께 늘어난다.
- 빈 그룹은 저장 시 서버가 거부하므로 화면도 저장 전에 막고 사유를 띄운다("조건이 없으면 모든 주문이 편입됩니다").

### 6.3 편집 — 우: 미리보기

주문일 범위(선택) + `[미리보기 실행]` → `편입 N / 대상 M`과 **주문 전건 목록**. 각 행을 펼치면 그룹별 통과 여부와 조건별 `기대값 — 실제값`이 나온다.

제외된 주문도 사유와 함께 보여주는 것이 이 패널의 존재 이유다. 저장 전에 "무엇이 왜 빠지는지"를 확인하지 못하면, 이름과 실제 조건이 어긋난 전략이 그대로 운영에 나간다.

### 6.4 실행 버튼의 위치

`[전체 실행]`(목록) · `[이 전략 실행]`(편집)은 **실제 데이터를 바꾸는 업무 동작**이라 확인 다이얼로그를 거친다. 호출 API는 전략 관리가 아니라 업무 도메인(`POST /outbound/waves/stgy-exec`)이다.

지금 이 버튼이 전략 화면에 있는 것은 **출고 웨이브 화면이 아직 없기 때문**이다. 웨이브 화면이 생기면 실행 진입점은 그쪽으로 옮긴다(전략 화면에는 미리보기만 남긴다).
