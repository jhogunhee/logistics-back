WMS 전략 분석 · 전략유형 22 + 적용구분 70

출고 할당·분배 전략
어느 재고를 꺼내고, 모자라면 누구에게 줄 것인가

할당 전략(전략유형 22)은 WMS에서 가장 정교하게 연결된 전략이다 — 적용구분 10~70마다 Spring Bean 하나가 대응하고, 공통 엔진이 이들을 조합 순회한다. 분배는 별도 전략유형이 아니라 할당 전략의 구분 70을 재사용해 "재고가 부족할 때 누구에게 얼마를 줄지"를 결정한다. 소스코드와 Company/dbData 운영 덤프로 검증했다.

분배 진입점OutbDivisionServiceImpl.saveDivisionStgy()
실행 단위상품별 병렬 쓰레드 · REQUIRES_NEW

1 · 목표

이 전략이 존재하는 이유

주문에 재고를 붙이는 일은 "어느 위치의 어느 로트를, 어떤 순서로, 얼마나"라는 네 가지 결정의 조합이다. 할당·분배 전략은 그 결정을 규칙으로 만든다.

선입선출의 자동화

제조일자·입고일자 오름차순(FEFO/FIFO) 같은 재고 소진 순서를 전략으로 정의해, 오래된 재고부터 나가게 한다. 재고할당순서(50)의 역할.

꺼낼 위치의 규칙화

피킹 로케이션 먼저, 없으면 보관 로케이션 — 재고위치(10)와 to로케이션(40)이 Loop 조합으로 후보 위치를 순서대로 시도한다.

부족할 때의 공정한 배분

재고 < 요청이면 분배(70)가 작동한다. 균등분배(출고단위·전량·주문비율)로 나누거나, 우선납품처 조건을 만족하는 주문에 먼저 준다.

부족분의 체계적 기록

할당하지 못한 수량은 사라지지 않고 결품(SHOTGE_QTY)으로 남아 후속 보충·재할당·마감의 근거가 된다.

웨이브 전략(21)이 엔진을 필터 하나로 쓰는 반면, 할당 전략(22)은 적용구분 7종을 역할 분담시켜 정렬·필터·조회조건·수량정책·분배까지 전부 규칙으로 움직인다. 같은 3계층 테이블에서 출발하지만 연결 밀도가 전혀 다르다.

2 · 구조

적용구분 하나 = Spring Bean 하나

3 · 할당 실행 과정

call() 한 사이클 — 상품별 쓰레드에서 벌어지는 일

재고할당 화면에서 전략할당을 실행하면 WmsBaseOutbAlocService가 웨이브의 주문을 AllocationTarget으로 변환해 BaseAllocationStgService.call()을 호출한다.

1

전략 선택 getStgyTarget(…, "C00031")

전략 마스터의 적용대상(거래처유형·출고유형)을 첫 주문 데이터와 비교해 전략코드 하나를 확정하고 전체 주문에 일괄 적용한다. 대상값 없는 전략은 무조건 매칭.

2

주문 정렬 — 구분 60

납품처코드순 Comparator로 targetList를 정렬한다. 순차할당에서 앞선 주문이 재고를 먼저 소진하므로, 이 정렬이 곧 우선권이다.

3

상품별 그룹 분할 → 병렬 쓰레드

상품 단위로 묶어 allocationExecutor에서 REQUIRES_NEW 트랜잭션으로 병렬 실행. 재고조회는 SELECT FOR UPDATE — 다른 쓰레드가 같은 상품을 잡고 있으면 row lock 대기, 초과 시 "동일상품 재고 작업으로 인해 취소" 오류.

4

전략 Loop — apply() 조합 순회로 재고 수집

Loop 대상 구분은 40 to로케이션 × 10 재고위치(sortSeq순). 조합마다 콜백이 실행된다:

  • 구분 30 출고수량 — 주문수량/출고단위 정책 + 허용 재고상태 확보
  • 구분 40 to로케이션 — 고정로케이션 조회 또는 통과
  • 구분 10 재고위치 — 조건을 재고조회 쿼리에 병합 → InvnCom.selectAlocTargetProdInvnList
  • 과할당 차감 — 피킹로케이션의 기할당 수량을 로트별로 가용재고에서 제외
  • 구분 20 출고제약 — 제조일자 잔여비율% 미달 재고 필터
  • 통과 재고를 invnGroup에 전략코드와 함께 누적
조합 순회 예 (덤프의 OAL0001 기준) — to로케이션 1건 × 재고위치 2건 = 2회 반복:
[적재로케이션, 로케이션유형=04 피킹] → 피킹존 재고 수집
[적재로케이션, 로케이션유형=03 보관] → 보관존 재고 수집
5

재고 정렬 — 구분 50

수집된 재고 전체를 제조일자 ASC → 입고일자 ASC → 로케이션코드 ASC처럼 다중 기준으로 정렬. 리스트 맨 앞 재고부터 소진된다 = 선입선출.

6

재고 vs 요청 비교 — 갈림길

재고 ≥ 총요청 → 순차 할당
  • 주문 순서대로 allocateResult() 실행
  • 재고 행을 앞에서부터 소진하며 로트·로케이션·수량 확정
재고 < 총요청 → 분배(70) 실행
  • 분배 APLY를 조합 순회하며 주문별 전략수량 산정
  • 산정된 수량 한도 안에서 할당 실행
7

결과 반영

  • AllocationResult 콜백으로 재고 예약 반영 (가용수량↓ · 할당수량↑)
  • 할당 못한 잔량은 결품(shotgeQty) 생성 — 전량 실패한 주문도 결품 0할당 행으로 기록
  • 작업로그(WorkLogParam, 업무유형 30/300) 저장
수기할당은 이 파이프라인을 타지 않는다 — 전략 실행 없이 전략코드 매핑(setAplyStgyCode)만 수행한다.

4 · 분배 실행 과정

같은 Bean, 두 개의 무대

분배 Bean(구분 70)은 할당 도중(재고 부족 시)과 총량피킹 후 분배 화면 (OutbDivisionServiceImpl.saveDivisionStgy) 두 곳에서 실행된다. 분배 화면 쪽 흐름:

1

대상 선별 — 상태 430 (총량피킹 확정)

웨이브의 분배 대상 중 출고진행상태 430인 주문만 골라 AllocationTarget으로 변환. 요청수량은 지시수량(ODR_QTY).

2

전략 선택 + 피킹확정 재고 적재

getStgyTarget(…, "C00031")으로 할당 전략(22)을 그대로 선택하고, 상품별로 피킹확정된 총량 재고(selectDivisionPickingCfmList)를 재고그룹에 담는다.

3

지시수량 vs 피킹확정수량 비교

확정 ≥ 지시 → 순차 배분
  • 전 주문 전략수량 = 요청수량으로 놓고 allocateResult()
확정 < 지시 → 분배전략 실행
  • apply(…, includeList=[70]) — 분배 APLY만 조합 순회
  • 우선분배: 조건(우선납품처 등) 미충족 주문 exclude
  • 주문별 전략수량 누적 (같은 APLY는 1회만, 잔여요청으로 상한)
  • 매 순회 후 allocateResult()로 실제 배분 확정
4

분배 결과 저장 saveWorkList

주문·로트·로케이션·분배수량(DIV_QTY)을 작업목록(TWM_OB_WRK_LST, 상태 610)에 기록하고 출고 디테일의 수량·결품을 갱신한다.

6 · 덤프·코드에서 발견한 특이점

실무에서 조심할 것들

코드를 따라가며 확인된, 화면 설명만으로는 알 수 없는 실제 동작.

1

출고제약 C10·D03을 전략에 넣으면 할당 전체가 실패한다

출고제약 Bean에서 C10 역순제한과 D03 유통기한(잔여비율%)은 미구현 상태로 E099 예외를 즉시 던진다 (AllocationStgyBean.java:164,203). 입고검수의 같은 제약 3종은 전부 구현돼 있는 것과 대조적 — 전략 화면에서는 등록이 가능하므로, 등록 즉시 해당 상품 할당이 예외로 중단된다.

2

분배단위 판정에 항상 참인 조건식 버그가 있다

분배 Bean의 단위 분기 else if(DIV_CD_PERC.equals(DIV_CD_PERC))는 상수를 자기 자신과 비교해 항상 참이다 (AllocationStgyBean.java:572,626). 의도는 applyData와의 비교 — 결과적으로 01·02가 아닌 모든 값(오타 포함)이 조용히 주문비율 분배로 처리되고, 마지막 오류 분기는 죽은 코드다.

3

"우선분배의 무엇을"과 "누구에게"는 저장 위치가 다르다

분배량 단위(출고단위/전량/주문비율)는 우선·균등 공통으로 적용기준값(C01524)에 저장되고, 우선분배의 대상 선별은 적용조건(C00023: 우선납품처순서=1 등)으로 판정된다. 덤프의 OAL0001 분배 ③이 정확히 이 구조다 — 화면 라벨만 보고 "우선분배 단위=우선납품처"로 읽으면 동작을 오해한다.

4

할당 시점과 분배 시점의 부족은 서로 다른 사건이다

덤프 사례에서 할당(300)은 재고 충분으로 분배 없이 끝났지만, 피킹에서 1EA를 못 채우자 분배 화면(610)에서 같은 분배 Bean이 다시 실행됐다. 분배전략은 "할당 재고 부족"만이 아니라 "피킹확정 < 지시"에도 대응하는 이중 안전망이다.

5

동일상품 동시 할당은 row lock으로 직렬화된다

상품별 쓰레드가 재고를 SELECT FOR UPDATE로 잡으므로, 다른 웨이브가 같은 상품을 할당 중이면 대기하고 초과 시(ORA-30006) "동일상품 재고 작업으로 인해 취소되었습니다"로 해당 상품만 실패한다 — 전체 할당이 죽지 않는다.

6

수기할당은 전략의 바깥에 있다

수기할당은 전략 파이프라인을 실행하지 않고 전략코드 매핑만 남긴다. 재고할당순서·출고제약이 적용되지 않은 할당이 데이터에 정상적으로 존재할 수 있다는 뜻이다.
