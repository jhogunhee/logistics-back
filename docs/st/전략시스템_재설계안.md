# WMS 전략 시스템 재설계안

> 대상 스택: **Spring Boot 3.x + JPA(Hibernate 6) + React(TypeScript)**
> 근거 문서: `docs/입고검수적치전략.html` · `docs/출고웨이브전략.html` · `docs/출고할당분배전략.html` (기존 시스템 분석, 2026-08-02)
>
> 전제: 기존의 공통 3계층 테이블(`TWM_SG_STGY` / `_APLY` / `_COND`)과 공통코드 체인은 **가져가지 않는다.**
> 최우선 요구사항은 두 가지 — ① 전략마다 고유한 비즈니스 로직이 있다는 것, ② 관리자가 화면에서 설정·관리할 수 있다는 것.

---

## 1. 설계 원칙

기존 시스템 분석에서 발견된 문제는 대부분 "범용 테이블 + 공통코드로 무엇이든 등록 가능하지만, 구현 여부는 아무도 보장하지 않는다"에서 나왔다. 새 설계는 다음 5개 원칙으로 그 원인을 구조적으로 제거한다.

| # | 원칙 | 기존 문제와의 대응 |
|---|---|---|
| P1 | **화면에 보이는 옵션 = 코드에 구현된 실행기.** 관리자 화면의 선택지는 코드 레지스트리에서 파생된다. 공통코드 테이블에 옵션을 추가하는 것으로는 화면에 나타나지 않는다. | 출고제약 C10·D03 등록 시 E099 즉시 예외 / 적치조건 D02 빈 구현으로 무조건 통과 |
| P2 | **정의(데이터)와 실행(코드)의 분리.** 관리자가 저장하는 것은 "정의"이고, 정의는 타입 있는 파라미터로 검증된다. 문자열 연산자 코드·자유입력 기준값은 쓰지 않는다. | 조건비교 인자 순서 반전 버그, 항상 참인 비교식(`DIV_CD_PERC.equals(DIV_CD_PERC)`) |
| P3 | **전략 유형별 독립 도메인 모델.** 검수·적치·웨이브·할당은 입력과 출력이 본질적으로 다르므로 테이블·엔티티·서비스를 각자 갖는다. 공유하는 것은 패턴(레지스트리, 이력, 미리보기)뿐이다. | 같은 3계층 테이블을 유형마다 전혀 다른 의미로 사용 (웨이브=필터, 할당=7슬롯, 입고=자체쿼리) |
| P4 | **설정 → 미리보기(Dry-run) → 적용 워크플로.** 모든 전략은 실행 로직을 순수 함수에 가깝게 유지해, 저장 전에 같은 로직으로 시뮬레이션할 수 있다. | 전략명과 실제 조건이 어긋난 채 운영된 데이터 (반품출고 웨이브 → 실제 조건 일반출고) |
| P5 | **실행 재구성 가능성.** 전략 수정 시 리비전을 남기고, 실행 결과에는 사용된 리비전 번호와 판정 근거를 기록한다. | 전략코드만 남아 과거 실행을 재구성할 수 없던 문제, "왜 이 주문이 편성 안 됐죠?" 대응 불가 |

### 2.2 공통 커널이 제공하는 것 / 제공하지 않는 것

**제공하는 것** — ① 실행기 메타데이터 규약(Descriptor/ParamSpec)과 레지스트리, ② 파라미터 검증기, ③ 전략 헤더 공통 필드(`@MappedSuperclass`), ④ 리비전 스냅샷, ⑤ 실행 로그 규약, ⑥ 메타데이터 REST API.

**제공하지 않는 것** — 공통 실행 엔진. 기존 `LodisStgyService.apply()` 같은 범용 순회 엔진은 만들지 않는다. 각 전략의 실행 흐름은 해당 도메인 서비스가 명시적 코드로 소유한다. (기존 분석에서 확인했듯 실행 의미가 유형마다 다르므로, 억지로 공통화하면 다시 "겉만 공통"이 된다.)

## 3. 공통 커널 상세

> **[2026-08-02 개정 — 커널 축소 결정]** 이 절의 Descriptor/ParamSpec/레지스트리(§3.1–3.2)는
> 1차 구현 후 **enum 방식으로 축소했다.** 구현체 5개(방식 3·규칙 2)·파라미터 2개 규모에서
> 범용 플러그인 장치는 이해 비용이 이득을 초과한다고 판단했기 때문이다. 현재 구조:
>
> - 구성요소 = **enum** (`PutawayMethod`, `InspectionRule`). name()이 DB code, 상수가
>   label·설명·판정 로직·파라미터 검증(`validatePara`)을 함께 가진다. 상수 추가 = 화면
>   선택지·저장 검증·실행에 동시 반영 (P1·P2는 그대로 성립하고, switch 누락은 컴파일 에러라 오히려 강해짐).
> - 메타 API는 enum을 `ComponentResponse(code, name, description, deprecated)`로 직렬화한다.
>   파라미터 폼은 프런트 `RuleParamForm`에 규칙별 고정 폼 — 서버 검증과 화면 폼이 두 곳이 되므로
>   **규칙 파라미터를 바꿀 때는 반드시 양쪽을 같이 고친다.**
> - §3.3(전략 헤더)·§3.4(필드 레지스트리 = 조건 필드 enum)·§3.6(실행 로그)·§3.7(메타 API)은 그대로다.
> - §3.5(리비전)는 **조회 전용으로 축소** (같은 날 2차 개정): 스냅샷 기록·조회는 유지하되
>   복원(스냅샷 재저장)·삭제된 전략 재생 흐름은 제거 — 프로세스정의서 §4.3 개정 참조.
> - **[2026-08-03 3차 개정 — 적치 적용대상 축소]** §5의 적치 전략 헤더에서 범용 적용대상
>   조건(tgt_cond)·우선순위(prty)를 제거하고 **발주구분(odr_dvsn) 단일 선택**(전체/정상/긴급,
>   유형당 1개 UNIQUE)으로 교체했다 — 단계 조건(line_cond)과 역할이 겹쳤고, 적용대상의 원래
>   용도(레거시 일반/반품 선택)가 반품 스코프 아웃으로 소멸했기 때문. 단계의 loc_cond는
>   "적치위치 지정(존 업무유형 IN 최대 1건)"으로 의미를 좁혔다(조건이 아니라 적용기준값).
>   개념 구분: **조건**(이 조건일 때만 적용 — 단계 line_cond) vs **적용기준·적용기준값**
>   (이 값을 적용 — 방식·적치위치·정렬). 상세는 프로세스정의서 §3.3 개정 참조.
>
> **재도입 기준**: 구성요소가 도메인당 10개를 넘거나 파라미터 스키마가 다양해져(출고웨이브·할당 구현 시점에
> 재평가) 손코딩 검증이 반복되면, 그때 이 절의 원안(Descriptor/ParamSpec/레지스트리)으로 되돌린다.
> 아래 §3.1–3.2 원문은 그 재도입 설계안으로 남겨둔다.

### 3.1 실행기 메타데이터 — Descriptor / ParamSpec

모든 전략 구성요소(검수 규칙, 적치 추천방식, 할당 슬롯 구현체…)는 자기 자신을 설명하는 Descriptor를 선언한다. **이 선언이 관리자 화면 폼의 유일한 원천이다.**

```java
public record ComponentDescriptor(
        String code,              // 저장에 쓰이는 안정 식별자. 예: "SHELF_LIFE_PCT"
        String name,              // 화면 표시명. 예: "유통기한 잔여비율"
        String description,       // 관리자에게 보여줄 설명 (동작을 문장으로)
        List<ParamSpec> params    // 이 구성요소가 받는 파라미터 스키마
) {}

public record ParamSpec(
        String key,               // 예: "minPercent"
        String label,             // 예: "최소 잔여비율(%)"
        ParamType type,           // NUMBER | TEXT | SELECT | MULTI_SELECT | BOOLEAN | DATE
        boolean required,
        List<Option> options,     // SELECT 계열일 때 선택지 (정적 또는 optionSource로 동적)
        String optionSource,      // 동적 선택지 소스. 예: "locationTypes", "outboundTypes"
        BigDecimal min, BigDecimal max,   // NUMBER 범위 검증
        String defaultValue
) {}
```

- `optionSource`는 기준정보(로케이션유형, 출고유형 등)에서 선택지를 채워야 할 때 사용한다. 프론트는 `GET /api/strategy-meta/options/{source}`로 조회한다.
- 파라미터 값은 저장 시 서버에서 `ParamValidator`가 스키마 대비 검증한다. 검증 실패는 저장 자체를 거부한다 — "등록은 되는데 실행하면 예외"인 상태를 만들지 않는다.

### 3.2 레지스트리

```java
public interface StrategyComponent {
    ComponentDescriptor descriptor();
}

@Component
public class StrategyComponentRegistry {
    // Spring이 주입한 구현체 목록을 유형별로 인덱싱
    private final Map<Class<?>, Map<String, StrategyComponent>> byType;

    public <T extends StrategyComponent> T get(Class<T> type, String code) {
        // 없으면 예외 — 단, 이 예외는 "저장된 정의가 배포본과 어긋남"을 뜻하는 운영 알람 대상
    }
    public <T extends StrategyComponent> List<ComponentDescriptor> descriptors(Class<T> type) { ... }
}
```

구현체를 코드에서 제거(또는 코드 변경)하면 기존 저장 정의가 깨질 수 있으므로 규칙을 둔다:

- 구성요소 `code`는 **절대 재사용·변경하지 않는다.**
- 구현체를 은퇴시킬 때는 삭제 대신 `deprecated=true`를 Descriptor에 표시 → 화면에서 신규 선택 불가, 기존 정의는 계속 실행. 완전 제거는 해당 code를 참조하는 정의가 0건임을 확인한 뒤에만.

### 3.3 전략 헤더 공통 필드

테이블은 유형별로 분리하지만 헤더 컬럼 구성은 통일한다.

```java
@MappedSuperclass
public abstract class StrategyBase {
    @Id @GeneratedValue Long id;
    String clientCd;          // 화주
    String centerCd;          // 센터
    String name;              // 표시명 (실행에 사용하지 않음 — P4의 미리보기가 이름/동작 불일치를 보완)
    int priority;             // 낮을수록 우선. 유형 내 선택 순서
    boolean active;           // 비활성화 = 실행 제외. 삭제 대신 사용 (기존 "테스트 제약이 전체 입고를 막던" 문제의 해법)
    Long currentRevisionNo;   // 마지막 저장 리비전
    // + 등록/수정자, 등록/수정일시 (Auditing)
}
```

**적용대상(이 전략을 어떤 건에 쓸지)** 은 헤더에 조건 목록으로 붙인다. 기존의 `C00031`(거래처유형·출고유형 매칭)에 해당하며, 웨이브 조건과 동일한 `FieldCondition` 구조(3.4의 필드 레지스트리)를 재사용한다. 비어 있으면 무조건 매칭.

### 3.4 필드 레지스트리 — 조건의 타입 안전화

기존의 "공통코드 4단 체인으로 조건기준 → 컬럼 매핑"을 코드로 옮긴다. 조건을 걸 수 있는 필드는 도메인별 enum으로 선언하고, 추출 함수·허용 연산자·값 선택지를 함께 정의한다.

```java
public enum OrderField implements ConditionField<OutboundOrderView> {
    OUTB_TYPE ("출고유형",  o -> o.outbTypeCd(),  Set.of(EQ, NE, IN), "outboundTypes"),
    FLEET_NO  ("차량편수",  o -> o.fleetNo(),     Set.of(EQ, NE, IN), "fleetNos"),
    CUSTOMER_TYPE("납품처유형", o -> o.customerTypeCd(), Set.of(EQ, NE, IN), "customerTypes"),
    CUSTOMER_GROUP("납품처그룹", o -> o.customerGroupCd(), Set.of(EQ, NE, IN), "customerGroups");
    // 필드 추가 = enum 상수 추가 → 화면에 자동 노출
}

public record FieldCondition(String fieldCode, ConditionOperator op, List<String> values) {}

public enum ConditionOperator { EQ, NE, IN, NOT_IN, GE, LE, BETWEEN, LIKE }
```

판정은 `field.extract(order)`와 `op.test(...)`로 수행한다. 인자 순서가 타입으로 고정되므로 기존의 "인자 순서 반전" 버그 계열이 사라진다. 연산자별 값 개수(BETWEEN=2, IN=1..n)도 저장 시 검증한다.

### 3.5 리비전 (변경 이력)

전략 저장(생성·수정)마다 전체 정의를 JSON 스냅샷으로 남긴다. 유형별 테이블을 나누지 않고 공용 한 테이블로 충분하다 — 스냅샷은 읽기 전용이므로.

```java
@Entity
public class StrategyRevision {
    @Id @GeneratedValue Long id;
    String strategyType;      // INSPECTION | PUTAWAY | WAVE | ALLOCATION
    Long strategyId;
    Long revisionNo;          // 전략별 1부터 증가
    @JdbcTypeCode(SqlTypes.JSON)
    String snapshot;          // 헤더 + 하위 구성 전체를 직렬화
    String savedBy; Instant savedAt;
}
```

- 실행 결과(웨이브 디테일, 적치지시, 할당결과)에는 `strategyId + revisionNo`를 함께 기록한다. → 이후 조건이 바뀌어도 "그때 왜 그렇게 판정됐는지"를 스냅샷으로 재구성할 수 있다.
- 화면에서는 리비전 목록 + 두 리비전 간 diff(JSON 비교)를 제공한다.

### 3.6 실행 로그 — 판정 근거의 구조화

```java
@Entity
public class StrategyExecutionLog {
    @Id @GeneratedValue Long id;
    String strategyType; Long strategyId; Long revisionNo;
    String triggerType;       // MANUAL | AUTO | PREVIEW
    String targetRef;         // 웨이브번호, 입고번호 등
    String resultSummary;     // "대상 12건 중 편입 9건" 등
    @JdbcTypeCode(SqlTypes.JSON)
    String decisionTrace;     // 건별 판정 상세 (아래)
    Instant executedAt; String executedBy;
}
```

`decisionTrace`는 건별로 `{대상, 결과, 탈락사유: [{조건, 실제값, 기대값}]}` 구조를 담는다. 관리자 화면에서 "이 주문이 왜 탈락했는지"를 조건 단위로 보여주는 데 쓴다. PREVIEW 실행도 같은 구조로 응답하되 저장은 선택적으로 한다(용량 관리를 위해 보존 기간 정책을 둔다).

### 3.7 메타데이터 API (공통)

| 메서드 | 경로 | 응답 |
|---|---|---|
| GET | `/api/strategy-meta/{domain}/components` | 해당 도메인에서 선택 가능한 구성요소 Descriptor 목록 (domain: `inspection-rules`, `putaway-methods`, `allocation-slots/{slotType}` …) |
| GET | `/api/strategy-meta/fields/{domain}` | 조건 필드 레지스트리 (필드코드, 표시명, 허용 연산자, optionSource) |
| GET | `/api/strategy-meta/options/{source}` | 동적 선택지 (기준정보 조회) |

프론트는 이 세 API만으로 모든 전략 편집 폼을 렌더링할 수 있어야 한다. **폼에 하드코딩된 선택지가 생기는 순간 P1이 깨진다.**

## 4. 입고검수 제약 (기존 전략유형 11)

### 4.1 도메인 모델

본질은 "검수 확정 직전에 로트를 검증하는 규칙 목록"이다. 기존 동작(등록된 제약은 전부 AND 실행, 하나라도 위반 시 저장 전체 차단)이 업무적으로 타당하므로 유지하되, 구조를 단순화한다.

```java
@Entity
public class InspectionPolicy extends StrategyBase {
    @OneToMany(mappedBy = "policy", cascade = ALL, orphanRemoval = true)
    @OrderBy("sortOrder")
    List<InspectionPolicyRule> rules;
}

@Entity
public class InspectionPolicyRule {
    @Id @GeneratedValue Long id;
    @ManyToOne InspectionPolicy policy;
    int sortOrder;
    String ruleCode;                      // 레지스트리의 InspectionRule code
    @JdbcTypeCode(SqlTypes.JSON)
    Map<String, Object> params;           // Descriptor의 ParamSpec으로 검증된 값
    boolean active;
}
```

화주·센터당 정책은 1개(uniqueness 제약)로 두는 것을 권장한다. 기존 시스템에서 "전략을 여러 개 만들어도 선택되는 게 아니라 합쳐져 전부 실행"이라는 혼란이 있었는데, 애초에 정책 1개 + 규칙 N개 모델이 실제 동작과 일치한다.

### 4.2 규칙 인터페이스와 초기 구현체

```java
public interface InspectionRule extends StrategyComponent {
    /** 위반 없으면 empty, 위반 시 사유 반환. 예외를 흐름 제어에 쓰지 않는다. */
    Optional<Violation> check(InspectionContext ctx, ParamValues params);
}

public record InspectionContext(
        String clientCd, String centerCd,
        String productCd, LocalDate inboundDate,
        LotAttributes lot,                 // 제조일자, 유통기한 등 타입 있는 로트 속성
        InventoryLotQuery lotQuery         // "이 상품의 기존 재고 최신 제조일자" 등 조회 포트
) {}
```

| code | 이름 | 파라미터 | 로직 (기존 분석 반영) |
|---|---|---|---|
| `LOT_DATE_REVERSE` | 역순제한 | `excludeSameDay: BOOLEAN` (기본 true) | 기존 재고의 최신 제조일자보다 과거인 제조일자 차단. 기존의 "당일 입고분 제외" 동작을 **명시적 파라미터로 승격** — 암묵 동작이던 것을 관리자가 보고 선택하게 한다. |
| `SHELF_LIFE_PCT` | 유통기한 잔여비율 | `minPercent: NUMBER (0~100)` | (전체유통일수 − 경과일수) / 전체유통일수 × 100 < minPercent → 차단. **기존 D02/D03은 계산이 완전히 동일했으므로 하나로 통합**하고, 위반 메시지에 잔여율·입고가능일을 포함한다. |

새 제약이 필요하면 구현체 + Descriptor를 추가하는 것으로 끝난다. 화면·저장·검증은 자동으로 따라온다.

### 4.3 실행과 미리보기

- 실행: 검수 확정 서비스가 `InspectionService.assertAll(policy, lines)`를 호출. 위반 목록을 모두 수집해 한 번에 반환한다(기존은 첫 위반에서 중단 → 관리자가 위반을 하나 고치면 다음 위반이 또 나오는 UX였다. 전체 위반을 한 번에 보여주는 편이 낫다). 저장 차단 여부는 호출 측이 결정.
- 미리보기: `POST /api/inspection-policies/{id}/preview` — 로트 정보 샘플(또는 미확정 검수 대기 건)을 입력하면 규칙별 통과/위반과 근거를 반환. DB 변경 없음.

## 5. 입고적치 (기존 전략유형 12)

### 5.1 설계 변경점: 카티전 곱 → 명시적 단계 목록

기존 구조는 "적치위치 APLY × 추천방식 APLY의 카티전 곱을 APLY_SEQ 순으로 순회"였다. 표현력은 있지만 관리자가 실행 순서를 머리로 계산해야 했다(분석 문서의 5게이트 사례처럼). 새 설계는 **관리자가 순서를 직접 배열하는 단계(Step) 목록**으로 바꾼다. 카티전 곱으로 표현되던 모든 조합은 단계를 그만큼 나열하면 동일하게 표현된다 — 표현력 손실 없이 예측 가능성만 얻는다.

```java
@Entity
public class PutawayStrategy extends StrategyBase {
    @OneToMany(...) @OrderBy("sortOrder")
    List<FieldCondition> targetConditions;   // 적용대상: 입고유형 등 (3.4 구조 재사용)

    @OneToMany(...) @OrderBy("sortOrder")
    List<PutawayStep> steps;

    // 전략 레벨 정책 (단계와 독립)
    @Embedded PutawaySplitPolicy splitPolicy;
    @OneToMany(...) @OrderBy("sortOrder")
    List<SortCriterion> locationSort;        // 후보 정렬: 적치순서/피킹순서/로케이션코드 × ASC/DESC
}

@Entity
public class PutawayStep {
    @Id @GeneratedValue Long id;
    int sortOrder;
    String methodCode;                        // 추천방식: FIXED_LOC | SAME_PRODUCT_LOC | EMPTY_LOC (레지스트리)
    @JdbcTypeCode(SqlTypes.JSON)
    Map<String, Object> methodParams;
    @OneToMany(...) List<FieldCondition> locationConditions;  // 로케이션유형=보관, 존=A … (후보 범위)
    @OneToMany(...) List<FieldCondition> lineConditions;      // 이 단계를 시도할 입고라인 조건 (포장단위=PALLET 등)
    boolean active;
}

@Embeddable
public class PutawaySplitPolicy {
    boolean splitByCaseQty;       // 입수량(박스) 배수로 절사 (기존: 낱개 혼적 방지)
    boolean skipWhenBelowOneCase; // 1케이스도 못 넣는 로케이션은 건너뜀
    Integer defaultMaxLoadQty;    // 로케이션 MAX 미설정 시 기본값. null이면 저장 시 경고 표시
    boolean countPendingMoves;    // 미완료 이동지시 수량을 점유로 계산 (기존 동작, 기본 true)
}
```

기존 분석의 특이점을 정책으로 승격한 부분:

- **MAX 미설정 = 999999 무제한** → `defaultMaxLoadQty`를 전략 화면에 노출하고, 미설정 로케이션이 후보에 잡히면 미리보기에서 경고를 보여준다.
- **미완료 이동지시 수량 점유 포함** → `countPendingMoves`로 명시. 기본 true(기존 동작 유지)지만, 동작이 화면에 보이므로 "가짜 만석" 상황을 관리자가 이해할 수 있다.

### 5.2 추천방식 구현체 (레지스트리)

```java
public interface PutawayMethod extends StrategyComponent {
    /** 후보 로케이션 조회. 정렬·수량분할은 서비스가 담당 — 구현체는 후보 선정만 */
    List<LocationCandidate> findCandidates(PutawayContext ctx, ParamValues params);
}
```

| code | 이름 | 후보 판정 |
|---|---|---|
| `FIXED_LOC` | 고정로케이션 | 고정로케이션이면서 고정상품 = 입고 상품 |
| `SAME_PRODUCT_LOC` | 적재로케이션 | 재고 > 0이고 같은 상품이 이미 있는 로케이션 |
| `EMPTY_LOC` | 빈로케이션 | 재고 0이고 고정상품 미지정 |

### 5.3 실행 알고리즘

```
입력: 입고라인(상품, 수량, 포장단위, 입수량), TO로케이션 미지정
1. 전략 선택: active + 적용대상 매칭 + priority 최소. 없으면 "적치전략 미설정" 오류
2. 잔여수량 = 지시수량
3. steps를 순서대로:
   a. lineConditions 불일치 → 다음 단계 (trace에 "조건 불일치" 기록)
   b. method.findCandidates() → locationConditions로 필터 → locationSort로 정렬
   c. 후보마다: 적재가능 = max(0, 최대적재 − 점유(현재고 + 미완료지시))
      - splitByCaseQty면 입수량 배수로 절사
      - 배정수량 > 0 이면 배정, 잔여수량 차감
      - 잔여수량 == 0 → 종료
4. 잔여수량 > 0 → 부분성공으로 반환 (배정분 + 미배정 잔여). 지시 생성 여부는 호출 측 정책
5. 결과를 재고이동지시로 저장 + ExecutionLog(단계별 trace)
```

미리보기: `POST /api/putaway-strategies/{id}/preview`에 입고라인(실존 입고번호 또는 가상 입력)을 주면 3까지 수행한 결과(단계별 게이트 통과/탈락, 로케이션별 배정 수량)를 반환. 기존 분석 문서의 "5게이트 표"가 그대로 화면이 된다고 생각하면 된다.

## 6. 출고웨이브 (기존 전략유형 21)

### 6.1 도메인 모델 — 기존 구조 계승, 표현만 타입화

기존의 "APLY끼리 OR, 같은 APLY 안 COND는 AND"는 조건 표현으로 적절했다. 구조를 그대로 가져오되 이름을 직관적으로 바꾼다.

```java
@Entity
public class WaveStrategy extends StrategyBase {
    String waveNamePattern;       // 예: "{name}_{outbDate}" — 웨이브명 생성 규칙을 데이터로
    @OneToMany(...) @OrderBy("sortOrder")
    List<WaveConditionGroup> groups;      // 그룹끼리 OR
}

@Entity
public class WaveConditionGroup {
    @Id @GeneratedValue Long id;
    int sortOrder;
    @OneToMany(...) List<FieldCondition> conditions;   // 그룹 안에서 AND. OrderField 레지스트리 기반
}
```

- 조건이 0건인 전략은 **저장 자체를 거부**한다 (기존은 실행 시점에야 오류).
- 조건 필드 추가(납품처그룹 등 기존 미구현분)는 `OrderField` enum에 상수를 추가하면 화면에 자동 노출된다.

### 6.2 실행 서비스

기존 실행 흐름(금일 미생성 전략 선별 → 웨이브 마스터 생성 → 대상주문 조회 → 건별 판정 → 편입)은 업무적으로 검증된 흐름이므로 유지한다. 달라지는 것:

- 판정이 `WaveStrategyEvaluator.matches(order, strategy)` 순수 함수로 분리된다. 자동실행·선택실행·미리보기가 전부 이 함수를 공유한다.
- 편입 결과(`wave_line`)에 `strategyId + revisionNo` 기록.
- 자동실행 멱등성(하루 1회)은 유지하되, "이미 생성됨"을 오류가 아닌 정상 응답(skip 목록)으로 반환한다.
- 수동 편성은 기존처럼 허용하되 `assignedBy: MANUAL`을 라인에 남겨, "전략 조건과 안 맞는 주문이 웨이브에 있는" 상황을 화면에서 구분 표시한다 (기존 분석: 수동 편성이 전략 실행보다 많았다 — 금지할 게 아니라 가시화할 대상).

### 6.3 미리보기

`POST /api/wave-strategies/{id}/preview?outbDate=...` → 편성 대상 주문 전체에 대해 `{주문, 매칭여부, 그룹별 조건 판정 상세}`를 반환. 저장 전 정의(화면의 미저장 상태)로도 미리보기할 수 있도록, 요청 본문에 정의 JSON을 직접 받는 변형도 제공한다: `POST /api/wave-strategies/preview` (body = 정의 + outbDate). **이 API가 "이름과 조건이 어긋난 전략" 문제의 실질적 해법이다.**

## 7. 출고할당·분배 (기존 전략유형 22 + 적용구분 70)

### 7.1 슬롯 모델 — 기존 구분별 Bean 구조의 계승

기존 할당 전략의 "적용구분 = Bean 하나" 구조는 잘 설계된 부분이므로 골격을 계승하고, 슬롯을 enum으로 명시해 타입화한다.

```java
public enum AllocationSlotType {
    INVENTORY_FILTER,   // 기존 10 재고위치 — 다중, 순서 있음 (피킹존 먼저 → 보관존)
    CONSTRAINT,         // 기존 20 출고제약 — 다중
    QTY_POLICY,         // 기존 30 출고수량 — 단일
    INVENTORY_SORT,     // 기존 50 재고할당순서 — 단일 (다중 기준은 파라미터로)
    ORDER_SORT,         // 기존 60 주문순서 — 단일
    DISTRIBUTION        // 기존 70 분배 — 다중, 순서 있음
}
// 기존 40 to로케이션은 별도 슬롯 대신 QTY_POLICY와 같은 단일 설정으로 흡수하거나,
// 목적지 추천이 실제로 필요한 요건이 확정될 때 슬롯으로 추가한다 (기존 LOAD_LOC는 사실상 no-op이었다)

@Entity
public class AllocationStrategy extends StrategyBase {
    @OneToMany(...) List<FieldCondition> targetConditions;   // 적용대상 (거래처유형·출고유형)
    @OneToMany(...) @OrderBy("slotType, sortOrder")
    List<AllocationSlotConfig> slots;
}

@Entity
public class AllocationSlotConfig {
    @Id @GeneratedValue Long id;
    @Enumerated(EnumType.STRING) AllocationSlotType slotType;
    int sortOrder;                            // 다중 슬롯 내 순서
    String componentCode;                     // 해당 슬롯 타입에 등록된 구현체 code
    @JdbcTypeCode(SqlTypes.JSON)
    Map<String, Object> params;
    @OneToMany(...) List<FieldCondition> conditions;   // 우선분배의 대상 선별 등
    boolean active;
}
```

저장 시 검증: 단일 슬롯(QTY_POLICY 등)에 2건 이상 등록 불가, 필수 슬롯(INVENTORY_FILTER, QTY_POLICY, INVENTORY_SORT) 누락 시 저장 거부.

### 7.2 슬롯별 인터페이스와 초기 구현체

```java
public interface InventoryFilter extends StrategyComponent {
    InventoryQuerySpec toQuerySpec(ParamValues params);   // JPA Specification/QueryDSL 조건으로 변환
}
public interface AllocationConstraint extends StrategyComponent {
    boolean allows(InventoryLot lot, AllocationContext ctx, ParamValues params);
}
public interface QuantityPolicy extends StrategyComponent {
    long adjust(long requestedQty, OrderLine line, ParamValues params);  // 주문수량 그대로 / 출고단위 절사
}
public interface InventorySorter extends StrategyComponent {
    Comparator<InventoryLot> comparator(ParamValues params);   // 다중 기준: params에 [{field, dir}] 목록
}
public interface OrderSorter extends StrategyComponent {
    Comparator<OrderLine> comparator(ParamValues params);
}
public interface DistributionPolicy extends StrategyComponent {
    /** 부족 상황에서 주문별 배분 상한 수량 산정. 상태 변경 없음 — 산정만 */
    Map<OrderLineId, Long> distribute(long availableQty, List<OrderLine> targets, ParamValues params);
}
```

| 슬롯 | 초기 구현체 (code) | 비고 |
|---|---|---|
| INVENTORY_FILTER | `LOC_TYPE_FILTER`(로케이션유형), `LOC_FILTER`(로케이션 직접), `INVN_STATUS_FILTER`(재고상태) | |
| CONSTRAINT | `SHELF_LIFE_PCT` | 검수의 동명 규칙과 계산식을 공유(공통 유틸). **미구현 옵션은 레지스트리에 없으므로 화면에 아예 안 뜬다** — 기존 C10/D03 E099 문제의 구조적 해결 |
| QTY_POLICY | `ORDER_QTY`(과할당 불허), `UNIT_TRUNC`(출고단위 배수 절사) | |
| INVENTORY_SORT | `MULTI_SORT` — params: `[{field: MFG_DATE|INB_DATE|LOC_CD, dir: ASC|DESC}]` | FEFO/FIFO를 파라미터 조합으로 표현 |
| ORDER_SORT | `BY_CUSTOMER`(납품처코드순) | 필요 시 추가 |
| DISTRIBUTION | `EQUAL_BY_UNIT`(출고단위씩 라운드로빈), `EQUAL_FULL`(전량), `EQUAL_BY_RATIO`(주문비율), `PRIORITY`(조건 충족 주문 우선 — conditions로 우선납품처순위 등 판정) | 분배량 단위와 대상 선별을 분리 저장하던 기존 구조를 유지하되, 화면에서 한 카드에 함께 보여줘 오독을 방지 |

분배(70)는 기존처럼 **별도 전략 유형으로 만들지 않는다.** 할당 중 재고 부족과 총량피킹 후 확정 부족, 두 무대에서 같은 슬롯 구성이 재사용되는 기존 구조가 옳다.

### 7.3 실행 파이프라인

```
1. 전략 선택: targetConditions 매칭 + priority
2. 주문 정렬: ORDER_SORT
3. 상품별 그룹 → 병렬 실행 (REQUIRES_NEW, 재고 비관적 잠금)
   ├─ 재고 수집: INVENTORY_FILTER 슬롯을 sortOrder 순으로 —
   │    각 필터의 QuerySpec으로 조회 → 기할당 수량 차감 → CONSTRAINT 필터 → 누적
   ├─ 재고 정렬: INVENTORY_SORT
   ├─ 요청수량 산정: QTY_POLICY
   ├─ 재고 ≥ 총요청 → 순차 할당 (정렬된 재고를 앞에서부터 소진)
   │  재고 < 총요청 → DISTRIBUTION 슬롯을 sortOrder 순으로 순회하며 주문별 상한 누적
   │                   (같은 슬롯 1회만, 잔여요청으로 상한 클램프) → 상한 내 할당
   └─ 미할당 잔량 → 결품 기록 (0할당 주문도 결품 행으로)
4. 결과 저장 + ExecutionLog (재고 수집 단계별 건수, 분배 슬롯별 산정치 trace)
```

동시성은 기존 방식(상품별 스레드 + `SELECT FOR UPDATE` 직렬화, 실패는 해당 상품만) 유지. JPA에서는 `@Lock(PESSIMISTIC_WRITE)` + `jakarta.persistence.lock.timeout` 설정으로 구현하고, 타임아웃 시 해당 상품만 실패 처리한다.

### 7.4 미리보기

`POST /api/allocation-strategies/{id}/preview?waveNo=...` — 잠금·저장 없이 1~3의 산정만 수행. 응답: 주문별 예상 할당/결품, 재고 수집 단계별 건수, (부족 시) 분배 슬롯별 산정 상세. 분배 화면용 미리보기도 동일 서비스의 시뮬레이션 모드로 제공한다.

## 8. REST API 설계 요약

CRUD는 4개 도메인이 동일한 패턴을 따른다. `{domain}` = `inspection-policies` | `putaway-strategies` | `wave-strategies` | `allocation-strategies`.

| 메서드 | 경로 | 설명 |
|---|---|---|
| GET | `/api/{domain}` | 목록 (화주/센터/활성 필터) |
| GET | `/api/{domain}/{id}` | 상세 (하위 구성 포함) |
| POST | `/api/{domain}` | 생성 — 파라미터 스키마 검증 + 리비전 1 생성 |
| PUT | `/api/{domain}/{id}` | 수정 — 검증 + 리비전 증가 |
| PATCH | `/api/{domain}/{id}/active` | 활성/비활성 토글 |
| POST | `/api/{domain}/{id}/preview` | 저장된 정의로 미리보기 |
| POST | `/api/{domain}/preview` | **미저장 정의**(body)로 미리보기 — 편집 중 실시간 확인용 |
| GET | `/api/{domain}/{id}/revisions` | 리비전 목록 / `{no}` 로 스냅샷·diff |
| GET | `/api/{domain}/{id}/executions` | 실행 로그 (판정 trace 포함) |

- 메타데이터 API는 3.7 참고.
- 실행(실제 반영) API는 전략 도메인이 아니라 업무 도메인(검수확정, 적치지시, 웨이브실행, 할당실행)에 둔다. 전략은 업무 서비스가 주입받아 쓰는 정책이다.

## 9. React 화면 설계

### 9.1 공통 컴포넌트 (전 도메인 재사용)

| 컴포넌트 | 역할 |
|---|---|
| `DynamicParamForm` | Descriptor의 `ParamSpec[]`을 받아 폼 렌더링 (NUMBER→숫자입력+범위, SELECT→드롭다운(optionSource 조회), …). 검증 메시지도 스키마에서 파생 |
| `ComponentPicker` | 레지스트리 Descriptor 목록에서 구성요소 선택. deprecated는 기존 선택분만 표시 |
| `ConditionBuilder` | `FieldCondition[]` 편집기. 필드 레지스트리 API 기반 — 필드 선택 → 허용 연산자만 노출 → 값 입력(optionSource). 웨이브 조건, 적용대상, 우선분배 조건, 적치 라인/로케이션 조건에 전부 재사용 |
| `SortableStepList` | 순서 있는 목록 편집 (drag & drop). 적치 Step, 분배 슬롯, 재고필터 순서에 사용 |
| `PreviewPanel` | 미리보기 결과 표시. 건별 통과/탈락 + 탈락 사유(조건, 실제값, 기대값) 표 — 기존 분석 문서의 "게이트 표"를 UI로 |
| `RevisionHistory` | 리비전 목록 + diff 뷰어 |

### 9.2 화면 구성

```
/strategies
├── /inspection        검수 정책: 규칙 카드 목록 (추가 = ComponentPicker → DynamicParamForm)
├── /putaway           적치 전략: 단계 목록(SortableStepList) + 분할정책 + 정렬 / 우측 PreviewPanel
├── /wave              웨이브 전략: 조건그룹 빌더 (그룹 사이 "OR" 구분선, 그룹 안 "AND") / 우측 PreviewPanel
└── /allocation        할당 전략: 슬롯 섹션별 편집 (필터·제약·수량·정렬·분배) / 우측 PreviewPanel
```

편집 화면은 공통 레이아웃을 쓴다: **좌측 = 정의 편집, 우측 = 미리보기.** 편집 중 정의를 `POST /preview`(미저장 body)로 보내 실시간 확인 → 확인 후 저장. "저장하면 곧 운영 반영"이라는 긴장을 UI 워크플로가 흡수한다.

### 9.3 타입 공유

Descriptor/ParamSpec/FieldCondition 등 메타 구조는 백엔드 응답 그대로 TypeScript 타입을 정의해 사용한다(OpenAPI Generator 권장). 프론트에 도메인 지식을 중복 구현하지 않는다 — 프론트가 아는 것은 "스키마를 렌더링하는 법"뿐이어야 한다.

## 10. 구현 순서 제안

| 단계 | 범위 | 이유 |
|---|---|---|
| 1 | core (Descriptor·레지스트리·ParamValidator·StrategyBase·Revision·ExecutionLog) + 메타데이터 API | 이후 모든 도메인의 토대. 작게 유지 |
| 2 | **웨이브** 전체 (엔티티→서비스→CRUD API→미리보기→React 화면) | 가장 단순한 도메인으로 패턴을 끝까지 검증. `ConditionBuilder`·`PreviewPanel` 등 공통 컴포넌트가 여기서 완성됨 |
| 3 | **검수** | 규칙 2종으로 작음. `DynamicParamForm` 완성 |
| 4 | **적치** | Step 모델 + 수량분할. `SortableStepList` 완성 |
| 5 | **할당·분배** | 가장 복잡 — 슬롯 6종 + 병렬 실행 + 분배 재사용. 1~4에서 만든 부품을 전부 재사용 |
| 6 | 실행 로그 조회 화면, 리비전 diff, 로그 보존 정책 | 운영 편의 기능 마무리 |

## 11. 기존 문제 → 새 설계 대응 요약

| 기존 분석에서 확인된 문제 | 새 설계의 대응 |
|---|---|
| 미구현 옵션(C10·D03) 등록 시 실행 예외 E099 | 화면 옵션이 레지스트리에서 파생 — 미구현은 화면에 없음 (P1) |
| 적치조건 D02 빈 구현 → 무조건 통과 | 동일 — 구현 없이는 등록 경로 자체가 없음 |
| 조건비교 인자 순서 반전 / 항상 참인 비교식 | 타입 있는 `FieldCondition` + enum 연산자 (P2) |
| D02/D03 동일 계산 중복 | `SHELF_LIFE_PCT` 하나로 통합 |
| 전략명과 조건 불일치 운영 데이터 | 미리보기 워크플로 + 이름은 실행에 미사용 명시 (P4) |
| 검수 전략 "여러 개 만들어도 전부 합산 실행" 혼란 | 정책 1개 + 규칙 N개 모델로 실제 동작과 구조 일치 |
| 테스트 제약 잔존 시 전체 입고 차단 | 규칙·전략 단위 active 플래그, 삭제 대신 비활성화 |
| 적치 카티전 곱의 실행 순서 예측 곤란 | 명시적 순서의 Step 목록 |
| MAX 미설정 = 무제한 999999 암묵 동작 | `defaultMaxLoadQty` 정책으로 노출 + 미리보기 경고 |
| 과거 실행 재구성 불가 (전략코드만 기록) | 리비전 스냅샷 + 실행 결과에 revisionNo 기록 (P5) |
| 판정 사유 불투명 ("왜 편성 안 됐나") | ExecutionLog의 decisionTrace — 조건 단위 탈락 사유 |
| 수동 편성이 전략 실행보다 많음 (비가시) | 수동/전략 편입 출처를 라인에 기록해 화면에서 구분 |
