# 자동발주 설계 (2026-08-25)

창고 전체 재고가 발주점 아래로 떨어진 상품을 매일 새벽 벤더별 **입고주문(작성 상태)** 으로 제안하는 흐름. 확정(→ ASN)은 사람이 누른다. **반품입고(`2026-08-25-rtngs-inbound-design.md`) 뒤에 착수한다** — 같은 `oms_ib_order`를 건드리므로.

정기보충(`SpmtScheduler`)이 「보관존 → 피킹 고정로케이션」 내부 이동만 내는 것과 짝이다 — 그건 창고 안에서 자리를 옮기는 일이고, 이건 창고에 없는 물건을 밖에서 들여오는 일이다. 틀은 같다: 산정 `plan` → 발행 `issue` → 스케줄러가 대상별로 호출.

## 1. 문서 흐름

```
prod_vndr(상품×벤더: 발주점·상한·MOQ·리드타임)
        │
   매일 04:00  AtoOdrScheduler ── plan ──▶ 벤더별 제안(라인 = 발주점 미달 상품)
                                  │
                                issue ──▶ oms_ib_order(status = CREATED, odr_dvsn = ATO)  벤더 1곳 = 주문 1건
                                                      │
                                              사람이 확정 ──▶ ib_order (기존 경로 그대로)
```

- **새 문서를 만들지 않는다.** 자동발주는 입고주문의 구분 하나(`ODR_DVSN = ATO`)다 — 헤더-라인 CRUD · 확정 · 확정취소 · 삭제를 그대로 쓴다. 잘못된 제안은 지우면 끝.
- **CREATED에서 멈춘다.** 자동으로 ASN까지 내려보내면 기준값이 틀렸을 때 창고가 오지 않을 물건을 기다린다. 정기보충이 이동지시를 바로 내는 것과 다른 이유는, 이동은 창고 안의 일이라 되돌리기 쉽고 발주는 바깥(벤더)과의 약속이기 때문이다.
- 의존 방향: `omsback → wmsback` 세 번째 접점으로 **읽기 전용 포트 `ProdStockPort`** 를 둔다(아래 3절). wmsback은 omsback을 모른다.

## 2. 데이터

### 산식 — 설계의 중심

```
aval      = Σ inv(보유 − 예약 − 보류)          전 로케이션(스테이징 포함), 반품존(zon.biz_dvsn = RTNGS) 제외
openAsn   = Σ ib_line(expct − rcvd − rjct)     ib_order.status ≠ CONFIRMED, odr_dvsn ≠ RTNGS
openOdrEa = prod.toEaQty(Σ oms_ib_line.odr_qty, inbUomCd)   oms_ib_order.status = CREATED, odr_dvsn ≠ RTNGS
net       = aval + openAsn + openOdrEa

대상     : net < min_qty
shortEa  = max_qty − net
odrQty   = max( ceil(shortEa ÷ eaQtyOf(inbUomCd)), min_odr_qty )      ← 입고단위
expct_de = today + max(lead_days)                                     ← 벤더 주문 라인 중 최대
```

- **중복 발주 방지는 플래그가 아니라 산식이 한다.** 한 발주 건은 어느 시점이든 세 항 중 정확히 하나에만 산다 — CREATED 주문(`openOdr`) → 확정되면 ASN(`openAsn`) → 검수되면 재고(`aval`). 겹치는 구간이 없어 어제 낸 주문이 오늘 `net`에 들어 있고, `net ≥ max ≥ min`이라 다시 잡히지 않는다. 정기보충이 「오고 있는 지시 잔량」을 유입으로 얹는 것과 같은 원리.
- ASN이 결품 채로 입고확정되면 잔량이 사라져 다음 주기에 그만큼 재발주된다 — 의도.
- 반품을 두 곳에서 뺀다 — 반품존 재고는 할당 후보가 아니고(반품입고 스펙), 반품 ASN·주문은 양품 보장이 없고 라인 단위가 출고단위라 환산도 갈린다. 빼는 편이 코드도 짧다.
- MOQ가 상한을 넘겨도 그대로 낸다 — 상한으로 자르면 MOQ의 뜻이 없다.
- `rjct` 항은 반품입고가 `ib_line.rjct_qty`를 넣었을 때만.

### 공급 마스터 — `prod_vndr`

```sql
CREATE TABLE prod_vndr (
    prod_vndr_id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    prod_id      BIGINT  NOT NULL,
    vendor_id    BIGINT  NOT NULL,
    min_qty      BIGINT  NOT NULL,             -- 발주점 (EA)
    max_qty      BIGINT  NOT NULL,             -- 발주 상한 (EA)
    min_odr_qty  BIGINT  DEFAULT 1 NOT NULL,   -- 최소주문수량 (입고단위)
    lead_days    INTEGER DEFAULT 1 NOT NULL,   -- 리드타임 (일)
    prty         INTEGER DEFAULT 1 NOT NULL,   -- 대표 벤더 우선순위, 작을수록 우선
    created_at … updated_by,                   -- fxng_loc와 동일
    CONSTRAINT uq_prod_vndr UNIQUE (prod_id, vendor_id),
    CONSTRAINT ck_prod_vndr_qty CHECK (min_qty >= 0 AND max_qty >= 1 AND min_qty <= max_qty
                                       AND min_odr_qty >= 1 AND lead_days >= 0 AND prty >= 1)
);
CREATE INDEX ix_prod_vndr_vendor ON prod_vndr (vendor_id);
```

- **`prod`에 컬럼을 두지 않는 이유** — 리드타임·MOQ는 상품이 아니라 「그 벤더에서 그 상품을 살 때」의 값이다. 벤더가 둘이면 두 벌이다. 고정로케이션 마스터(`fxng_loc`)가 「상품×로케이션」인 것과 같은 꼴이라 화면·가드 패턴을 그대로 쓴다.
- 발주점·상한은 **EA**(창고 수량과 비교), MOQ는 **입고단위**(발주 수량의 단위). 화면 툴팁에 명시.
- **대표 벤더 = `prty` 최소, 동률이면 `prod_vndr_id` 최소.** `prmry_yn` + 부분 유니크 인덱스보다 단순하고, 마스터 행 하나를 지워도 다음 벤더가 자연히 대표가 된다.
- 마스터에 없는 상품은 대상이 아니다(`fxng_loc`에 없는 상품이 정기보충 대상이 아닌 것과 같다).
- 삭제 가드: `ProdVndrRefChecker`가 `ProdRefChecker` · `VendorRefChecker` 둘 다 구현(`@Order(4)`, WMS·OMS 참조 뒤) → "상품 거래처(발주 기준)". `prod_vndr` 행 자체는 어떤 문서도 참조하지 않으므로 행 삭제 가드는 없다.
- 이름: 사전 추가는 **「리드타임 = LEAD」 하나**. 발주는 별도 약어 없이 `ODR`(`odr_dvsn` · `odr_qty` 선례), 발주점/상한은 `min_qty`/`max_qty`(`fxng_loc` 재보충점/보충상한 선례), MOQ는 `min_odr_qty`, 우선순위는 `prty`(`loc.pikng_prty` 선례). 테이블명은 `거래처 = VNDR` + `prod_uom` 조합 규칙 → `prod_vndr`, FK 컬럼은 참조 PK명 그대로 `vendor_id`.

### 공통코드

`ODR_DVSN`에 `ATO 자동발주`(srt_seq 4). 정상 `NRML`이 아니므로 화면은 뱃지로 구분한다(긴급 앰버와 다른 하늘색).

### 시드

시드 상품 3종(신라면 멀티팩 · 서울우유 1L · 왕교자 만두)을 `VD-0001`~에 연결. 한 행은 `min_qty`를 시드 재고보다 크게 잡아 첫 산정에서 제안이 나오게 한다 — 검증용임을 주석에 남긴다. `ON CONFLICT (prod_id, vendor_id) DO NOTHING`.

## 3. 서비스

### 재고 포트 (`wmsback.inventory`)

```java
public interface ProdStockPort {
    record ProdStock(Long prodId, long avalQty, long openAsnQty) {}
    /** 상품별 가용(반품존 제외) + 미확정 ASN 잔량(반품 제외). 없는 상품은 맵에 없다 → 호출측 0 */
    Map<Long, ProdStock> stockByProd(Collection<Long> prodIds);
}
```

- 구현 `ProdStockQueryRepository` — `JPAQueryFactory`만 드는 읽기 전용 포트(`SpmtQueryRepository`와 같은 꼴, 3파일 삼각형 아님). 쿼리 둘: `InvQueryExpressions.avalQty().sum()` group by prod / `ib_line` 잔량 sum group by prod.
- `omsback → wmsback` 접점이 「작업문서 둘」에서 **「+ 읽기 전용 재고 포트」** 로 는다. 쓰기는 없다. `CLAUDE.md`에 기록.

### OMS 미확정 발주 합

`OmsIbLineRepositoryCustom.openOdrQtyByProd(ids)` — CREATED · RTNGS 제외, group by prod, **입고단위**. `Prod.toEaQty`로 EA 환산 — javadoc 「호출 지점 세 곳」에 네 번째로 올린다(같은 OMS→WMS 경계라 규칙 위반이 아니다).

### `AtoOdrService` (`omsback.inbound`)

- `AtoOdrQtyCalc` — 순수 static: `net(...)`, `ceilDiv(a, b)`, `proposedQty(shortEa, eaPerUom, minOdrQty)`. `shortEa ≤ 0`이면 0. 테스트의 주 대상.
- `plan(cond)` `readOnly` — `prodVndrRepository.findAllForPlan()`(fetch join) → 상품당 대표 벤더 → `ProdStockPort` + `openOdrQtyByProd` 두 번 호출(N+1 없음) → 산식 → 벤더별 그룹(`vndrCd` 순), 라인 0건 벤더 제외.
- `issue(request)` `@Transactional` — 검증(벤더 · 예정일 · 라인 ≥ 1 · `odrQty ≥ 1` · 각 상품이 그 벤더의 `prod_vndr`에 등재 — 백도어 차단) → `OmsIbOrderSaveRequest(vendorId, expctDe, odrDvsn = "ATO", picNm = null, rmk = "자동발주 yyyy-MM-dd 산정분")` → **`OmsIbOrderService.create` 재사용**(채번 · 검증 중복 없음). `net`은 재검증하지 않는다 — CREATED에서 사람이 보고, 산정이 CREATED를 유입으로 세므로 재조회하면 자연히 사라진다. 정기보충의 2회 검증과 다른 점.
- `issueAll(list)` — `BatchExecutor`로 벤더 단위 REQUIRES_NEW(`OmsIbOrderService.confirmAll`과 같은 틀). 화면 · 스케줄러 둘 다 이걸 부른다.

### `AtoOdrScheduler`

`SpmtScheduler` 복제. `@Scheduled(cron = "${ato-odr.cron}")`, 기본 `0 0 4 * * *`(정기보충 03:00 뒤 — 순서 의존은 없다, `net`은 창고 전체 합이라), `"-"`면 비활성. `plan` 실패는 로그 · return, `issueAll` 결과를 `[ATO] 자동발주 — 부족 상품 N건 · 벤더 M곳 중 k곳 생성 · j곳 실패` 로 남긴다. 실행 이력은 로그가 전부(정기보충과 같다). 예외를 밖으로 던지지 않는다.

## 4. 주변 영향

- **적치 전략 적용대상** `PtawyStgyService.ODR_DVSNS = Set.of("NRML","URGT")` — 반품입고가 이 필터를 없애기로 했으니 남아 있으면 `"ATO"` 추가.
- `SchedulingConfig` 주석 「현재 스케줄 작업은 정기 보충 하나」 → 둘.
- 입고주문 등록/수정 화면의 구분 드롭다운은 공통코드를 읽으므로 `ATO`가 자동으로 나온다 — 사람이 자동 제안을 고칠 때 선택지에 있어야 하므로 감추지 않는다.

## 검증 시나리오

`POST /master/prod-vndrs/bulk`로 `min_qty`를 재고보다 크게 등록 → `GET /oms/ato-odr/plan`에 제안 → `POST /oms/ato-odr` → `GET /oms/inbound-orders?status=CREATED`에 `odrDvsn = ATO` 건 → **plan 재조회 시 같은 상품이 사라짐(멱등)** → 확정 뒤에도 없음(ASN 항으로 이동) → 벤더 삭제 시 "상품 거래처(발주 기준)에서 사용 중" 거부. 스케줄러는 `ATO_ODR_CRON="0 */2 * * * *"`로 띄워 두 번째 주기에 「생성할 제안 없음」이 찍히는지.
