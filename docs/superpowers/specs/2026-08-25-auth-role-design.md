# 인증과 역할 설계 (2026-08-25)

로그인 · 사용자 마스터 · 역할별 API 차단 · 역할별 메뉴. 지금은 `SecurityConfig`가 `permitAll`이고 작성자(`created_by`)가 `admin` 고정이라 「누가 했는지」가 남지 않는다. 이 구멍을 채운다.

일부러 하지 않는 것 — 화면·버튼 단위 권한 편집 화면, 역할 만들기 화면, 리프레시 토큰, 회원가입, 지시자/실행자(PDA) 분리. 역할 목록은 코드(enum)에 고정한다.

## 1. 역할

실제 센터는 **업무 구역(입고 · 재고 · 출고)별로 담당이 다르고**, 그 위에 센터 전체를 보는 관리자, 옆에 주문을 넣는 영업/구매팀, 시스템 설정을 만지는 IT가 있다. 이게 메뉴 섹션과 1:1로 맞아서 그대로 역할이 된다.

| 코드 | 한글 | 허용 범위 |
|---|---|---|
| `ADMR` | 시스템관리자 | 전부. 마스터 · 공통코드 · 채번 · **사용자 관리**는 여기만 |
| `CENT_ADMR` | 센터관리자 | 입고 · 재고 · 출고 업무 전부 + **전략 설정**(검수기준 · 적치 · 웨이브 · 할당은 IT가 아니라 운영 판단) |
| `ODR_PIC` | 주문담당 | 입고주문 · 출고주문 등록 · 확정 (`/oms`) |
| `IB_PIC` | 입고담당 | ASN · 검수 · 적치 · 입고확정 (`/inbound`) |
| `INV_PIC` | 재고담당 | 이동 · 보류 · 로트/속성변경 · 실사 · 보충 (`/inventory`) |
| `OUTB_PIC` | 출고담당 | 웨이브 · 할당 · 피킹 · 출고확정 (`/outbound`) |
| `INQ` | 조회 | 모든 화면 GET만 |

**한 사용자가 역할을 여러 개 가질 수 있다.** 작은 센터는 한 명이 입고+재고를 같이 보는 게 흔한데, 단일 역할이면 「입고재고담당」 같은 조합 역할이 계속 생긴다. 판정은 「필요한 역할 중 하나라도 있으면 통과」다.

이름은 사전대로다 — 관리자 `ADMR` · 센터 `CENT` · 담당자 `PIC` · 조회 `INQ` · 주문 `ODR` · 출고 `OUTB`. 입고 · 재고는 사전이 `INB` · `INVN`이지만 코드 전체가 `Ib*` · `Inv*`라 그쪽을 따른다(테이블 접두와 같은 예외).

## 2. 데이터

```sql
CREATE TABLE usr (
    usr_id      BIGINT       GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    login_id    VARCHAR(30)  NOT NULL,
    usr_nm      VARCHAR(50)  NOT NULL,
    pwd         VARCHAR(100) NOT NULL,          -- BCrypt 해시
    created_at / created_by / updated_at / updated_by,
    CONSTRAINT uq_usr_login_id UNIQUE (login_id)
);

CREATE TABLE usr_role (
    usr_id      BIGINT       NOT NULL,
    role        VARCHAR(20)  NOT NULL,
    CONSTRAINT pk_usr_role PRIMARY KEY (usr_id, role),
    CONSTRAINT ck_usr_role CHECK (role IN ('ADMR','CENT_ADMR','ODR_PIC','IB_PIC','INV_PIC','OUTB_PIC','INQ'))
);
```

- 프로젝트 규칙대로 FK 없음 · `us_yn` 없음. 퇴사자는 삭제한다. `created_by`엔 `login_id` 문자열이 남으므로 이력은 깨지지 않는다.
- `login_id`는 「`_id`는 PK/FK」 관례와 겹친다. 사람이 「아이디」라 부르는 값이고 사전의 `아이디 ID`가 그 뜻이라 그대로 쓴다. 사전에 `로그인 LOGIN` · `역할 ROLE` 두 단어를 추가한다.
- 시드: `admin`(ADMR) · `center`(CENT_ADMR) · `order`(ODR_PIC) · `inbound`(IB_PIC) · `stock`(INV_PIC) · `outbound`(OUTB_PIC) · `viewer`(INQ). 비밀번호는 전부 `1234`의 BCrypt 해시 리터럴. 마이그레이션은 `docs/migration-usr.sql` — DO 블록 하나, 존재 확인으로 재실행 안전.

## 3. 백엔드

### 의존 방향

- `common.security` — `JwtTokenProvider`(발급 · 검증) · `JwtAuthFilter`(헤더 → `SecurityContext`) · `SecurityConfig`(URL 규칙). **DB를 보지 않는다.** 토큰 claim에 `login_id` · `usr_nm` · `roles`가 들어 있어 그걸로 권한을 세운다 → `common`이 `mdm`을 import하지 않는다.
- `mdm.usr` — `Usr` · `UsrRole`(엔티티, `@ElementCollection`으로 `usr_role` 매핑) · `Role` enum · `AuthController` · `UsrController` · `UsrService` · `UsrRepository`. 두 앱이 공유하는 마스터라 `mdm`이다.
- `JpaConfig.AuditorAware` → `SecurityContext`의 `login_id`. 인증 없는 실행(정기보충 스케줄러)은 `system`. DB 기본값 `'admin'`은 그대로 둔다(INSERT에 값이 늘 실린다).

### 토큰

- `jjwt 0.12` (api / impl / jackson). HS256.
- 비밀키 `jwt.secret=${JWT_SECRET:...}` — 로컬 기본값은 `application.properties`에 32바이트 이상 임의 문자열을 박아 두고, 배포 환경은 환경변수로 덮는다. 만료 `jwt.expiry-hours=${JWT_EXPIRY_HOURS:12}`.
- claim: `sub`=login_id, `nm`=usr_nm, `roles`=["ADMR",…]. 리프레시 없음 — 만료되면 재로그인.

### API

| | 경로 | 역할 |
|---|---|---|
| 로그인 | `POST /auth/login` `{loginId, pwd}` → `{token, loginId, usrNm, roles}` | 누구나 |
| 내 정보 | `GET /auth/me` → `{loginId, usrNm, roles}` (새로고침 시 토큰 유효성 확인 겸) | 로그인 |
| 비밀번호 변경 | `PUT /auth/pwd` `{curPwd, newPwd}` | 로그인 |
| 사용자 목록 | `GET /master/usrs?keyword=` | ADMR |
| 사용자 저장 | `POST /master/usrs/bulk` `[{_status, usrId, loginId, usrNm, pwd, roles[]}]` | ADMR |

`UsrSaveRequest`가 필수 · 역할 1개 이상 · 신규 행 비밀번호 필수를 보고(`toEntity` / `updateEntity`), 서비스가 DB를 보는 검사를 한다 — 아이디 중복, 자기 자신 삭제 금지, **마지막 ADMR 삭제 · 역할 해제 금지**. 수정 행의 `pwd`는 값이 있을 때만 초기화(빈 값 = 유지).

### URL 규칙 (`SecurityConfig` 한 곳)

```
POST /auth/login                          → permitAll
     /master/usrs/**                      → ADMR  (GET 포함 — 사용자 목록은 관리자만)
GET  /**                                  → authenticated (INQ 포함)
비GET /auth/**                             → authenticated
비GET /master/**                           → ADMR
비GET /strategy/**                         → ADMR, CENT_ADMR
비GET /oms/**                              → ADMR, ODR_PIC
비GET /inbound/**                          → ADMR, CENT_ADMR, IB_PIC
비GET /inventory/**                        → ADMR, CENT_ADMR, INV_PIC
비GET /outbound/**                         → ADMR, CENT_ADMR, OUTB_PIC
그 외                                      → denyAll
```

- 컨트롤러에 `@PreAuthorize`를 흩뿌리지 않는다. 접두가 곧 업무 구역이라 규칙 하나로 끝난다. 새 컨트롤러가 접두를 지키면 자동으로 규칙 안에 든다.
- 전략 화면의 「미리보기」가 POST라 INQ는 미리보기를 못 한다. 조회 성격이지만 예외를 두면 규칙이 지저분해져 그대로 둔다.
- 토큰 없음/만료 → 401 `{message}`, 역할 부족 → 403 `{message}`. `GlobalExceptionHandler`가 아니라 `SecurityConfig`의 `authenticationEntryPoint` · `accessDeniedHandler`가 낸다(필터 단계라 핸들러에 안 닿는다).
- CORS는 기존 `CorsConfig` 유지. `Authorization` 헤더가 허용 목록에 있는지 확인한다.

## 4. 프론트 (`C:\wms-front`)

- `src/api/authApi.js`(login · me · changePwd) · `src/api/usrApi.js`(list · saveAll).
- `src/auth/AuthContext.jsx` — `{user, login, logout, hasRole}`. 토큰과 `{loginId, usrNm, roles}`를 `localStorage`에. `axios.js`는 이미 `localStorage.token`을 Bearer로 붙이고 401이면 `/login`으로 보낸다 — 그대로 쓰고, **403은 「권한이 없습니다」 토스트**를 인터셉터에 추가한다. 기존 `sessionStorage.loginUser`는 지운다.
- `Login.jsx` — 임시 통과를 `authApi.login`으로 교체. 폼 필드명 `userId` → `loginId`.
- `App.jsx` — `<Layout/>` 라우트를 `RequireAuth`로 감싼다(토큰 없으면 `/login`). `/master/usrs` 라우트 추가.
- `Sidebar.jsx` — MENU 항목에 `roles` 필드, `hasRole`로 필터. 하단 사용자 영역을 `usrNm` · 역할 라벨 · 실제 로그아웃(`logout()` → `/login`)으로.
  - INQ: 전 메뉴 보임(조회만 되니 화면은 다 본다)
  - 각 `*_PIC`: 모니터링 + 자기 섹션. CENT_ADMR: 모니터링 + 입고 · 재고 · 출고 + 전략. ADMR: 전부 + 「사용자 관리」
  - 메뉴 숨김은 편의일 뿐이고 막는 건 백엔드다 — URL로 들어가도 403.
- `pages/master/UsrMaster.jsx` — 벤더 관리와 같은 그리드 C/U/D 틀. 열: 아이디 · 이름 · 역할(다중 선택) · 비밀번호(신규는 필수, 수정은 입력한 경우만 초기화).
- 역할 한글 라벨은 프론트 상수 하나(`src/auth/roles.js`)에 둔다 — 백엔드는 코드만 안다.
