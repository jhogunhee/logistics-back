# 멀티센터 + TC(통과형) 설계 (2026-09-02)

지금 센터는 그대로 두고 **두 번째 센터를 TC(통과형)로** 붙인다. 온도대 분리(상온 센터 / 저온 센터)는 이번에 하지 않는다 — 아래 3절의 「주문 1 = 창고문서 1」을 즉시 풀어야 해서 크기가 배로 뛴다.

이 문서는 **조사 결과와 순서**를 박는 것이고, 구현 계획(`docs/superpowers/plans/`)은 범위를 정한 뒤 따로 쓴다.

## 1. 왜 TC를 두 번째 센터로 고르는가

센터를 하나 더 만드는 값(센터 축 도입)은 **어느 길로 가든 똑같이 든다** — 존·로케이션·재고·주문·작업문서가 전부 「센터 하나」 전제 위에 있어서, 기존 데이터를 센터 1로 채우고 QueryDSL 리포지토리와 화면 전 영역에 센터 필터를 붙이는 비용은 공통이다.

갈리는 것은 그 다음이다.

| | 온도대로 쪼개기 | **TC를 새로 붙이기** |
|---|---|---|
| 기존 데이터 | 존·로케이션·재고를 두 센터로 마이그레이션 | 전부 센터 1 그대로 |
| 주문 1:N 분할 | **즉시 필요** (3절) | 미룰 수 있음 — TC가 자기 주문을 받으면 |
| 회귀 위험 | 높음 — 돌아가던 센터를 건드린다 | 낮음 — 기존 흐름이 그대로 돈다 |
| 새 업무 | 없음 | 크로스도킹 (5절) |

통합테스트가 업무 흐름 단위로 짜여 있고 점검 SQL이 `inv_hist` 합계와 `inv` 스냅샷을 대조하는데, 기존 센터의 재고를 쪼개면 그 전제가 통째로 흔들린다. **돌아가는 것을 안 건드리는 쪽**을 고른다.

## 2. 지금 없는 것

### 센터 축이 없다

`docs/schema.sql` 전체에 `cent` / `center` / `site` / `warehouse_id` **0건**. 컬럼이 있어야 할 자리 어디에도 없다.

| 테이블 | 위치 | 컬럼 |
|---|---|---|
| `zon` | schema.sql:114 | `zon_cd, zon_nm, tmp_zon, strg_typ, biz_dvsn` |
| `loc` | :136 | `loc_cd, zon_id, tmp_zon, loc_typ, pikng_prty, ptawy_prty, max_qty` |
| `ib_order` | :817 | `ib_no, oms_ib_order_id, status, vendor_id, store_id, expct_de, odr_dvsn, cfm_dt` |
| `outb_order` | :1380 | `outb_no, oms_outb_order_id, status, outb_typ, vhcl_fltno, store_id, wav_id, …` |

`docs/design.md:7`이 전제를 명시한다 — 「**식품/음료 유통 물류센터 (단일 센터, B2B 점포 출고)** 를 가정한다」.

**재고 키는 컬럼을 안 늘려도 된다.** 재고는 상품 + Location + Lot이고 `loc`이 존을 통해 센터를 물므로, `inv`·`inv_hist`는 `loc`을 따라 자동으로 센터 스코프가 된다. 새 컬럼이 필요한 곳은 **문서 헤더**(`ib_order`·`outb_order`)와 채번 정도다.

### `CENT_ADMR`는 이름만 있는 권한 라벨이다

`Role.java:16`에 `CENT_ADMR("센터관리자")`가 있지만, 쓰이는 곳은 **URL 접두 기반 쓰기권한 판정뿐**이다(`SecurityRules.java:17-24`). 어떤 데이터도 센터 단위로 거르지 않는다. 지금 이름의 뜻은 「센터 = 시스템 전체를 보는 관리자」이지 복수 센터를 가르는 축이 아니다.

멀티센터의 값어치 절반이 「이 사용자는 이 센터만 본다」에서 나오므로, 센터 축을 넣을 때 **이 역할에 실제 스코프를 주는 것**이 함께 온다.

### 스테이징이 전역 싱글턴이고 온도대가 `DRY` 고정이다

`RCV-STAGE`·`SHIP-STAGE`는 온도대별로 있지 않고 **코드값 하나로 조회하는 단일 로케이션**이다.

```sql
-- seed-dev.sql:132
INSERT INTO zon (zon_cd, zon_nm, tmp_zon, strg_typ, biz_dvsn)
VALUES ('RCV-STAGE', '입고 스테이징', 'DRY', 'VRTL', 'INB')
```

즉 **저온 물건도 상온 스테이징에 잠깐 놓이는 모델**이다. 센터가 둘이 되면 이 상수를 드는 7곳(`CLAUDE.md`가 목록을 관리 중 — `IbLineRepositoryImpl` · `ReceivingService` · `PutawayService` · `PutawayTaskService` · `PikngTaskService` · `PikngService` · `OutbShmtService`)이 전부 **「센터별 해석」**으로 바뀌어야 한다. 이건 TC를 붙이든 온도대로 나누든 똑같이 걸린다.

## 3. 「주문 1 = 창고문서 1」이 4중으로 박혀 있다

온도대 분리를 미루는 근거이자, 나중에 풀 때의 목록이다.

| 층 | 위치 | 내용 |
|---|---|---|
| DB | schema.sql:877 · :1425 | `uq_ib_order_oms_active` · `uq_outb_order_oms` — 둘 다 평범한 전체 유니크 |
| 리포지토리 | `OutbOrderRepository:36` · `IbOrderRepository:15` | `Optional` 단건 반환. 2행이면 `IncorrectResultSizeDataAccessException` |
| 화면 | `OmsOutbOrderService:53` · `OmsIbOrderService:57` | **`Collectors.toMap`** — 2건이면 `Duplicate key`로 목록 화면 500 |
| DTO | `OutbOrderRef` · `AsnRef` | 단수 필드 (record) |

가장 단단한 것은 세 번째다. DB 제약을 풀어도 화면이 먼저 터진다.

푸는 순서가 필요해지면: 유니크를 `(oms_outb_order_id, cent_id)` 복합으로 → 리포지토리를 `List` 반환으로 → `toMap`을 `groupingBy`로 → `OutbOrderRef`를 컬렉션 필드로. 그리고 `OmsOutbOrderService.confirm()`의 라인 루프를 센터 기준으로 그룹핑하고 채번을 그룹당 1회로 바꾼다.

**출고는 온도대를 인지조차 하지 않는다.** 주문 경로의 `tmpZon`은 전부 표시용 응답 DTO뿐이고, 라인을 온도대로 가르는 코드는 한 줄도 없다. 웨이브·할당 전략 조건 필드에도 온도대가 없다(`WaveOrderField` · `AlocLineField` · `AlocTgtField` · `AlocInvnField`). 온도대로 센터를 나누면 **출고 전략 전체에 새 축을 넣는 일**이 딸려온다.

## 4. 크로스도킹 하드 가드 셋 — 그리고 왜 안 걸리는가

이 문서의 알맹이다. 통과형을 막는 것처럼 보이는 가드가 셋 있다.

| 위치 | 규칙 |
|---|---|
| `OutbAllocRepositoryImpl:314` | 할당 후보를 `loc.locTyp.eq(LocTyp.STORAGE)`로 제한 |
| `IbOrder:168` | 검수분이 전량 적치돼야 입고확정 |
| `InvMovService:128,134` | 스테이징은 재고이동의 출발지도 도착지도 될 수 없음 |

첫 번째의 주석이 특히 강하다 — 「**하드 가드 — 전략이 못 바꾸는 전제라 산정기가 아니라 조회가 갖는다**」. 전략 설정으로 우회할 수 없다.

**그런데 셋 다 「스테이징(`LocTyp.STAGE`) 재고를 쓰지 마라」는 규칙이다.** 분류 레인을 `STORAGE` 타입 로케이션으로 두면 셋 다 그대로 통과한다.

할당 후보 조건을 그대로 읽어 보면 분명하다 — `OutbAllocRepositoryImpl:311-324`.

```java
inv.prod.id.eq(prodId),
loc.locTyp.eq(LocTyp.STORAGE),                                  // 스테이징 제외
zon.bizDvsn.ne(BizDvsn.RTNGS).or(zon.bizDvsn.isNull()),         // 반품존 제외
avalQty().gt(0L)
```

**두 겹 다 「제외 목록」이지 「허용 목록」이 아니다.** 새 존 업무구분 `CRSDK`는 `RTNGS`가 아니므로 자동으로 후보에 든다. 레인 로케이션이 `STORAGE`면 첫 조건도 통과한다 — **코드 수정 없이** 레인 재고가 할당 후보가 된다.

반품존 조건의 주석이 이미 두 겹의 관계를 못박고 있다 — 「반품존 로케이션도 `locTyp`이 `STORAGE`라 위 조건만으로는 걸리지 않는다」. 유형과 존 업무구분이 서로를 대신하지 않는다는 것을 **설계자가 알고 두 겹으로 뒀다**(`BizDvsn` 클래스 주석도 같은 말을 한다).

```
입고 → 검수 → 적치(레인으로) → 입고확정      레인 적치도 적치다          ✓
     → 할당(레인 재고)                        레인이 STORAGE라 후보다     ✓
     → 피킹 → 출고확정                        기존 그대로                 ✓
재고이동은 쓰지 않는다 — 적치가 레인에 놓고 피킹이 빼간다                  ✓
```

**가드를 뒤집을 필요가 없다.** 레인은 스테이징이 아니라 보관 로케이션이고, 존 업무구분만 새로 둔다.

`BIZ_DVSN`에 `CRSDK`를 더하는 것은 **두 벌**이다 — 공통코드(`schema.sql:562-567`, 지금 `INB`·`OUTB`·`STRG`·`PIKNG`·`RTNGS`·`WRK`)와 **`BizDvsn` enum**. 그 enum의 주석이 「값 목록의 주인이 공통코드라 서비스가 특정 값에 결합하지 않는다는 규칙의 **명시적 예외**」라고 스스로를 설명한다. `CRSDK`는 그 예외를 하나 늘리는 일이고, 결합 지점을 한 곳에 모으는 기존 관례(`RplnDestinationResolver.inPikngZon` · `RtngsLocResolver.inRtngsZon`)를 따라야 한다.

### ⚠ 제외 목록이라는 것의 양날

새 존이 **자동으로 후보에 든다**는 것은 반대로 위험이다. `CRSDK` 존을 만드는 순간, **TC 레인 재고가 DC의 일반 출고 할당에도 후보로 잡힌다.** 같은 방식으로 걸러지는 곳이 셋 더 있다.

| 위치 | 조건 |
|---|---|
| `OutbAllocRepositoryImpl:320` | 자동할당 후보 |
| `AlocQueryRepository:70` | 할당 미리보기 후보 (위와 같아야 한다고 주석이 못박음) |
| `ProdStockQueryRepository:53` | **자동발주 순재고** — TC 재고가 전사 순재고에 섞인다 |

**그래서 8절의 순서가 뒤집힐 수 없다.** 센터 축(1단계)이 없는 상태로 TC 존만 만들면, TC에 놓인 물건이 DC 주문에 할당되고 자동발주 계산에도 섞인다. 센터 필터가 먼저다.

> 이 판단이 흔들리면 안 되는 이유: 저 세 가드는 각자 다른 사고를 막고 있다. 스테이징 할당은 「피킹이 보관 → SHIP-STAGE라 성립하지 않는다」를, 적치 완료 강제는 「안 온 물건을 왔다고 닫는 것」을 막는다. 레인을 STORAGE로 두는 것은 **가드를 우회하는 것이 아니라 애초에 그 대상이 아닌 것**이다.

## 5. 진짜 새로 필요한 것 — 사전할당

TC를 TC로 만드는 것은 로케이션 이름이 아니라 **할당 시점**이다.

| | DC | 크로스도킹 |
|---|---|---|
| 물건이 놓이는 곳 | 보관 랙 | 출고 레인 ← *로케이션 모델* |
| **할당 시점** | 재고를 쌓아두고 나중에 | **입고 전에 이미 정해짐** ← *알맹이* |

두 번째 줄이 본론이고, 첫 줄은 자리 이름이다. 지금 `ib_line`(입고 예정)과 `outb_line`(출고 주문)은 **서로를 모른다.** 이 매칭이 유일한 구조적 신규 개념이다.

**적치 도착지를 「그 물량이 배정된 점포의 레인」으로 푸는 장치**가 함께 필요한데, 형태는 이미 있다 — 보충 도착지를 「고정 자리 → 같은 상품이 있는 피킹존 → 빈 피킹존」 3단계로 푸는 `RplnDestinationResolver`가 본보기다. 크로스도킹은 「그 물량이 배정된 주문의 점포 레인」 한 단계로 푼다.

## 6. 크로스도킹 두 유형 — 사전분류형부터

| | 사전분류형 | 사후분류형 |
|---|---|---|
| 공급사가 | **점포별로 나눠서** 보냄 | 총량으로 보냄 |
| 센터가 하는 일 | 검품 → 해당 점포 레인 | 검품 → **분류(sorting)** → 레인 |
| 필요한 것 | ASN 라인에 점포가 실림 | 소터·DPS, 분류 작업·실적 |
| 실무 | 마트·대형 점포 | 편의점(다품종 소량이라 공급사가 못 나눔) |

**사전분류형부터 한다.** 지금 시스템이 점포 배송 B2B이고 상품이 14종 규모라 자연스럽고, 분류 작업·실적이라는 새 화면군이 붙지 않는다. 순서는 ASN 라인에 점포를 얹고 → 적치가 그 점포 레인으로 풀고 → 할당이 그 매칭을 존중하는 것이다.

사후분류형은 그 위에 얹는다.

## 7. 이미 있어서 재사용할 것

- **점포 유형 축이 이미 전략 조건이다.** `store_grp` · `store_typ`(시드 `CVS` 편의점 · `MART` · `FDSVC` 급식)가 웨이브 편성(`WaveOrderField:35-36`)과 할당 분배(`AlocLineField:34,36,37`) 조건 필드로 등록돼 있다. **업태별 처리 차이를 코드 수정 없이 전략 설정으로 표현할 수 있다** — 「편의점 주문만 따로 웨이브로」·「편의점에 먼저 배분」이 지금도 된다.
- **점포별 잔여수명 허용률**(`store.outb_life_rate`)이 이미 할당 필터로 흐른다 — `AlocLineTarget.of()` → `AlocRstrct.minPct()`. 업태마다 유통기한 요구가 다른 것이 이미 기준정보에 들어가 있다.
- **전략 커널 4종**(검수·적치·웨이브·할당)과 리비전·실행로그. TC의 적치 도착지 해석은 적치전략의 구성요소로 얹는다.
- **`omsback → wmsback` 접점 규율** — 작업문서 둘로 제한한 형태를 그대로 지킨다.

## 8. 순서

각 단계는 **독립적으로 배포 가능**해야 하고, 각 단계 끝에서 **기존 통합테스트가 전량 통과**해야 한다.

1. **센터 축** — `zon`(따라서 `loc`)에 `cent_id`, `ib_order`·`outb_order`에 `cent_id`. 기존 데이터 전부 센터 1. 스테이징 싱글턴 7곳을 센터별 해석으로. `CENT_ADMR`에 실제 스코프. 리포지토리·화면에 센터 필터.
2. **TC 센터 + 레인** — `BIZ_DVSN`에 `CRSDK` 추가, TC 존·레인 로케이션 시드. 기존 흐름(검수 → 적치 → 할당 → 피킹 → 출고)으로 굴려서 도는지 확인. **이 단계까지는 새 업무 로직이 없다.**
3. **사전할당** — `ib_line` ↔ `outb_line` 매칭, 적치 도착지 해석, 할당이 매칭을 존중.

1이 가장 크고 2가 가장 작다. 2까지 가면 「TC라는 이름의 작은 DC」가 돌고, 3이 그것을 TC로 만든다.

## 9. 미결정

- **센터 간 이고** — 한 센터 출고 = 다른 센터 입고. TC 입고를 공급사 직납으로만 하면 이번 범위 밖이고, DC → TC 이고를 넣으면 새 문서·새 화면이 붙는다. 멀티센터의 진짜 알맹이 중 하나.
- **점포 유형별 출고단위** — `prod.outb_uom_cd`가 **상품당 하나**라, 같은 상품을 편의점엔 낱개로 슈퍼엔 박스로 내보낼 수 없다. 포장 목록(`prod_uom`)은 여럿인데 「어느 점포엔 어느 단위」를 담을 자리가 없다.
- **배송 시간대** — `expct_de`가 `DATE`라 「몇 시 편」이 없다. 편의점 하루 2~3회 배송을 표현할 자리가 없다. TMS 조사(`[[wms-tms-missing-masters]]`)에서 나온 구멍과 같은 자리.
- **센터별 채번·전략 스코프** — 채번 규칙이 센터별인지 전사인지. 전략이 센터마다 다른지.
- **자동발주가 센터별인지 전사인지** — `ProdStockPort`가 「이 상품이 창고에·오는 중에 얼마나 있나」에 답하는데, 센터가 둘이면 질문 자체가 갈린다.
- **주문 1:N** — 이번엔 미루지만, 온도대 분리나 「한 주문이 DC와 TC로 갈리는」 경우가 오면 3절 목록을 풀어야 한다.

## 10. 이 문서가 하지 않는 것

`docs/design.md:7`의 「단일 센터」 전제는 **고치지 않는다.** 지금 코드의 사실이라 미리 고치면 거짓이 된다 — `CLAUDE.md`가 경고하는 「코드가 아직 따르지 않는 의도」를 늘리지 않기 위해서다. 1단계 구현과 함께 고친다.
